## 1. 设计定位与核心体验

### 1.1 一句话定位

**「你不是在打牌，你是在用牌指挥一个正在变强的英雄，在一座不知道出口在哪的地牢里做取舍。」**

### 1.2 三大设计支柱

| 支柱 | 含义 | 系统承载 |
|---|---|---|
| **P1 乘算爆发感** | 数值成长与卡牌效果必须**相乘**而非相加，让玩家在第 5 层感受到「我现在是个怪物」 | 属性碎片 + 卡牌系数化伤害（§7.5）+ 符文可组合乘区（§6） |
| **P2 空间即决策** | 六边形战场不是装饰，站位错误应该导致失败 | 体型系统 + 朝向/背击 + 推拉位移 + 地形危害 + 敌人预警（§8） |
| **P3 探索是赌博** | **你不知道 Boss 在哪。** 每推开一扇门都是一次赌注 | 盲探地图（§9.3）+ 腐蚀度（§9.4）+ 房间清空奖励 |

### 1.3 目标体验节奏（单局）

```
0-3 分钟   第1层：只有 攻击/防御/移动 三张基石卡 + 1武器 + 1符文，动作贫乏，靠基础操作过关
3-15 分钟  第2-4层：卡组成型，第一批符文进来，玩家开始"试组合"
15-30 分钟 第5-8层：属性碎片堆积，符文开始互相咬合，出现"一回合清场"的高潮
30-45 分钟 终章：Boss 用机制（而非数值）反制玩家的构筑，逼迫应变
```

**单局目标时长：35–50 分钟。**

## 2. 对标游戏拆解（我们抄什么，不抄什么）

这一节是设计依据，不是致敬清单。每条都标注了我们的处理。

### 2.1 《杀戮尖塔》Slay the Spire

| 机制 | 为什么有效 | 我们的处理 |
|---|---|---|
| **敌人意图预告（Intent）** | 把随机性从"结果"前移到"信息"，让玩家的每个决策都可归因。这是 StS 最重要的一条设计 | **完全继承并强化**：因为有战场，意图要额外显示**目标格子与波及范围**（借鉴《Into the Breach》） |
| **抽牌堆 / 弃牌堆 / 洗回三段循环** | 卡组是一个**可推算的概率系统**：玩家能算"这张牌还有几回合回来"。这是卡牌肉鸽策略深度的地基 | ✅ **D2 已确认全盘继承**（详见 §7.4） |
| **回合结束弃掉手牌** | 制造"这回合必须用完"的紧迫感；防止囤牌 | ✅ 继承 |
| **卡组即身份** | 卡组是玩家在这局的"角色"，比数值更有记忆点 | 继承，但因为我们有强数值，需刻意压制"数值盖过卡牌"（§7.5 系数化） |
| **移除卡牌是稀缺资源** | 让"拿一张烂卡"成为真实代价 | ❌ 改为**卡组容量上限 + 替换制**（D3 / §7.6） |
| **遗物改变规则** | 数值奖励是加法，规则奖励是乘法 | 由**符文**承载（§6），且符文的设计目标比遗物更激进（见 D6） |
| **能量经济（3 点）** | 极小的资源池 → 每点都痛 | 我们是 **5 点体力**。5 点比 3 点宽松，用"移动也要花体力"重新收紧（§7.3） |
| **精英风险回报** | 玩家主动选择困难 | 继承，但**精英房在盲探地图上不预先可见**（D4 的连带结果，见 §9.3） |

### 2.2 《暗黑地牢》Darkest Dungeon

| 机制 | 为什么有效 | 我们的处理 |
|---|---|---|
| **走廊—房间的地图结构** | 探索本身是一段有摩擦的旅程，不是菜单 | **继承为层内房间图**（§9.2） |
| **火把/光照：消耗性资源制造压力** | 玩家越贪，环境越恶劣 | **改造为「腐蚀度」**（§9.4）：进入的房间越多，怪物越强、掉落越好 |
| **未探明的地图 / 推门才知道里面是什么** | 探索的紧张感来自**信息缺失** | ✅ **D4 强化继承**：Boss 房也不可见。这是本作与 StS 最大的结构差异 |
| **压力 / 精神崩溃** | 第二条失败轴，制造叙事 | ❌ **v1 不做**。回合制卡牌已有 HP 一条失败轴，第二条会让新手劝退 |
| **队伍站位（4 人 × 前后排）** | 阵容构筑深度 | ❌ 改为**单英雄 + 六边形站位 + 体型系统**承载空间深度（D1/D8） |
| **永久死亡** | 提高每次决策的重量 | 单局内英雄死亡 = 本局结束（标准肉鸽），局外英雄不永久损失 |

### 2.3 《以撒的结合》The Binding of Isaac

| 机制 | 为什么有效 | 我们的处理 |
|---|---|---|
| **道具即时改变手感，且相互乘算** | "破坏平衡"本身是卖点。玩家追求的是找到 broken combo | **核心继承**。符文与装备允许出现明显 OP 的组合，我们不平衡掉它们，而是用**难度阶层**（§11.4）追上去 |
| **房间清空的节奏（进 → 清 → 拿 → 走）** | 极短的反馈闭环 | 继承：战斗结束**立刻**掉落，立刻吸收，不攒到层末结算 |
| **地图为房间格 + 迷雾，Boss 房要找** | 制造"再推一扇门"的张力 | ✅ **D4 继承**（以撒的 Boss 房也是要找的，且没有钥匙锁） |

### 2.4 《小丑牌》Balatro —— 符文系统的主要参照（D6）

| 机制 | 为什么有效 | 我们的处理 |
|---|---|---|
| **小丑卡是独立的、可自由组合的"加成牌"** | 没有官方"羁绊表"告诉你该凑什么，**组合是玩家自己发现的**。这带来的探索欲远超标签计数系统 | ✅ **D6 核心继承**：取消羁绊，符文各自独立 |
| **小丑卡通过共享的底层机制互相咬合** | 例：A「每打出第 3 张牌免费」+ B「打出 0 费牌时抽 1」→ 玩家自己拼出引擎 | ✅ 继承：符文全部挂在**统一触发时机表**（§6.3）上，组合自然涌现 |
| **小丑卡的顺序影响结算顺序** | 免费送一层玩家自己发现的深度 | ✅ 继承（§6.5）：符文槽有序，触发按槽位 1→6 结算 |
| **加/乘区分离，乘区是稀有的** | 让"找到乘区"成为追求 | ✅ 继承（§6.4）：绝大多数符文是加区/触发器，乘区符文稀有且醒目 |

### 2.5 《英雄联盟》海克斯强化 —— 符文的形态参照（D6）

| 机制 | 我们的处理 |
|---|---|
| **少量槽位，每个强化显著改变玩法** | 6 槽，且要求"规则改写型"符文占多数（§6.4） |
| **三选一，选了就锁定** | 继承：符文获取采用三选一；槽满时需覆盖（§6.6） |
| **强化本身是卡牌形态的 UI** | 继承（符文以卡牌形式陈列在英雄面板） |

### 2.6 《Into the Breach》—— 战场深度的主要参照

| 机制 | 我们的处理 |
|---|---|
| **敌人行动 100% 前置预告** | ✅ §8.6 |
| **地形推拉 = 主要伤害来源之一** | ✅ §8.5：推入尖刺/火焰/深坑/撞墙 |
| **单位少（3 个）但深度足够** | ✅ 这是 D1（单英雄）能成立的直接证据 |
| **单位有体积，占位本身是资源** | ✅ **D8 体型系统**（§8.2）把这一点做成了核心机制 |

### 2.7 补充参考

- **《Slice & Dice》/《Astrea》**：小规模、强数值、回合制肉鸽的节奏与信息密度范本。
- **《Monster Train》**：多层战场 + 位置分配，证明"卡牌 + 位置"可以共存而不臃肿。

## 3. 核心循环

### 3.1 三层嵌套循环

```
┌─ 元循环（跨局，小时级）───────────────────────────────┐
│  开局选英雄 → 打一局 → 死亡/通关 → 获得精魄            │
│  → 解锁卡牌/符文图鉴、提升英雄基础属性、点天赋         │
│  → 解锁更高难度阶层 → 再开一局                          │
│                                                          │
│  ┌─ 局循环（单局，35-50 分钟）──────────────────────┐   │
│  │  第 N 层：生成房间图（3~9 间，Boss 房位置未知）    │   │
│  │  → 盲探房间（战斗/事件/商店/宝藏/营地/Boss）       │   │
│  │  → 找到并击杀 Boss → 层奖励                        │   │
│  │  → 第 N+1 层（腐蚀度重置，怪物基线上升）           │   │
│  │                                                     │   │
│  │  ┌─ 战斗循环（单场，2-5 分钟）────────────────┐   │   │
│  │  │  进入 7×7 六边形房间，英雄按体型生成于(4,1)  │   │   │
│  │  │  → 回合：抽 5 张 / 恢复 5 点体力             │   │   │
│  │  │  → 打牌（移动/攻击/防御/技能）→ 入弃牌堆     │   │   │
│  │  │  → 结束回合（弃掉手牌）→ 敌方按预告行动      │   │   │
│  │  │  → 全灭敌人 → 掉落卡牌 + 属性碎片            │   │   │
│  │  └──────────────────────────────────────────────┘   │   │
│  └─────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

### 3.2 玩家在每一层要做的 4 个决策

1. **推哪扇门**（不知道里面是什么 × 腐蚀度成本 × 我还剩多少血）
2. **收哪张卡 / 挤掉哪张卡**（卡组容量上限强制取舍）
3. **符文装哪个槽 / 覆盖谁 / 排什么顺序**（6 槽有序，满了之后每次都是取舍）
4. **找到 Boss 房之后，是现在进，还是先把这层刷完**（腐蚀度会让 Boss 变强）

> 设计准则：**每一层至少让玩家做一次"痛的选择"。** 如果一层里所有选项都是纯增益，这一层的设计是失败的。

## 4. 英雄与属性系统

### 4.1 ✅ D1：单英雄／局（纯单人）

**一局操控 1 名英雄。4 名基准英雄 = 4 条可重玩的 build 路线（≈《杀戮尖塔》的 4 个角色）。不做联机玩法。**

| 项 | 确定内容 |
|---|---|
| 一局的我方单位数 | **1**（体型可能占 3 格，但仍是 1 个单位） |
| 4 名英雄的作用 | 4 套独立的 属性偏向 / 被动 / 基石卡变体 / 卡池标签 / **体型** → 4 种截然不同的玩法幻想 |
| 卡组归属 | 单一卡组，只服务当前英雄 → 构筑清晰，卡手概率低 |
| 装备 / 符文 | 3 槽 + 6 槽，均属于该英雄 |
| 单场战斗时长 | 目标 **2–5 分钟**（"爬塔"节奏能成立的前提） |

**单英雄的战场深度从哪来（这是 D1 的必要配套）：**

战场上只有 1 个我方单位，"站位"的深度不能靠单位数量，必须靠以下**五件套**。它们不是可选项，是 D1 能否成立的判据（见 R3）：

| # | 机制 | 让"站哪里"产生意义的方式 |
|---|---|---|
| 1 | **体型系统**（§8.2 / D8） | 你的身体本身占据 1/3/6 格 → 走廊、门口、狭道对你和对敌人意义不同 |
| 2 | **朝向 / 背击**（§8.2） | 敌人有朝向，从背面攻击有加成 → "绕后"值得花体力 |
| 3 | **推拉位移**（§8.5） | 击退/拉拽/换位 → 你可以改变敌人的位置，而不只是改变自己的 |
| 4 | **地形与危害**（§8.2 / §9.7） | 墙挡视线、尖刺/火焰区、深坑 → 把敌人推进去 = 位移即伤害 |
| 5 | **敌人意图预警**（§8.6） | 完整预告目标格 → "我该躲到哪一格"可计算，而非猜 |

> 《Into the Breach》每关也只有 3 个我方单位，深度全部来自"完全预警 + 推拉 + 地形 + 体积"。这条路径已被验证。

> **数据结构仍以 `Unit`（单位）为粒度**，而非"玩家"。因为敌方本来就是多单位，且保留了召唤物的可能（R3 的备选方案）。这不是为联机预留，而是战斗层本身的正确抽象。

### 4.2 四名基准英雄的设计意图

英雄不只是数值不同，必须**改变卡组的运作方式**（StS 的核心课）。每个英雄拥有：属性基线偏向、被动天赋（改写规则）、专属基石卡变体、专属卡池标签、**体型**。

| 英雄 | 体型 | 属性偏向 | 被动天赋（改写规则方向） | 基石卡变体 | 卡池标签 | 玩法幻想 |
|---|---|---|---|---|---|---|
| **骑士 Knight** | **1 格** | 生命↑↑ 防御↑↑ 敏捷↓ | 「格挡不在回合结束清空，可叠加至上限」→ 滚雪球型坦克 | 《攻击》→《盾击》（伤害受 DEF 加成，附带击退 1 格） | 守备 / 反击 / 嘲讽 / 位移抗性 | 站在原地，让敌人自己撞死 |
| **法师 Mage** | **1 格** | 攻击↑↑ 生命↓↓ 暴击↑ | 「体力上限 −1，但每回合抽牌 +2」→ 组合技型 | 《攻击》→《奥术飞弹》（射程 3，无视 1 点 DEF） | 范围 / 元素状态 / 抽牌 / 连锁 | 用一套连招覆盖半个战场 |
| **弓箭手 Ranger** | **1 格** | 敏捷↑↑ 暴击↑↑ 防御↓ | 「每回合首次移动免费；对射程 ≥3 的目标伤害提升」→ 风筝型 | 《移动》→《翻滚》（位移 2，位移后本回合首次攻击必暴） | 单体高爆 / 位移 / 陷阱 / 距离收益 | 永远不被摸到，但每一发都很痛 |
| **巨人 Giant** | **3 格** | 生命↑↑↑ 攻击↑ 敏捷↓↓ 暴击↓ | 「无法被击退；可碾压穿过 1 格敌人；相邻敌人移动距离 −1」→ 地形型 | 《防御》→《巨岩之躯》（获得格挡，并使相邻敌人下回合移动 −1） | 范围溅射 / 推拉 / 地形改造 / 控场 | 我的身体本身就是障碍物 |

> **巨人是 D8 体型系统在玩家侧的载体。** 他的核心体验是"我很难走进狭窄地形，但我一旦站在那里，谁也过不去"。这要求 §9.7 的地形模板库必须包含**狭道/门洞**类布局，否则巨人的体型只有缺点没有优点。

> **6 格体型不给玩家英雄使用（v1）**，仅用于精英怪与 Boss（§8.2）。原因：7×7=49 格的战场上，6 格占 12%，作为玩家单位会让走位空间过于局促。作为**可选的符文效果**（「你的体型变为 6 格」）是一个很有趣的高风险高回报选项，列入 §6.4 的设计方向。

### 4.3 六属性定义与作用域

| 属性 | 代号 | 主作用 | 次作用 | 设计意图 |
|---|---|---|---|---|
| **生命值** | `HP` | 上限；归零则本局结束 | — | 唯一失败轴 |
| **攻击力** | `ATK` | 所有伤害的乘区基数 | — | 主要成长快感来源 |
| **防御值** | `DEF` | 受击减伤 | 骑士的《盾击》伤害加成 | 让"堆防御"是一条真路线 |
| **敏捷值** | `AGI` | 战斗先手判定 | ① 闪避率 ② 移动卡额外位移 | 把"速度"拆成三种可感知收益，避免它变成鸡肋属性 |
| **幸运值** | `LUK` | 掉落数量/品质权重 | ① **暴击伤害倍率** ② 事件好结果概率 ③ 稀有卡/符文出现率 | 幸运必须影响**局内产出**才有养成动机 |
| **暴击率** | `CRIT` | 暴击触发概率 | — | 与 LUK 分工：CRIT 管"多久暴一次"，LUK 管"暴多痛" |

**关键分工原则：`CRIT` 决定频率，`LUK` 决定倍率。** 两个属性都不会成为废属性，且"暴击流"需要同时堆两者 → 产生真正的构筑取向。

### 4.4 属性公式形态（数值待调，此处只定形状）

> 所有常量以 `K_*` 占位。目标：**所有百分比属性走递减曲线，所有加法属性走线性**，防止后期数值崩坏。

**伤害计算管线**（严格按此顺序，实现时必须是单一函数，禁止散落各处）：

```
最终伤害 =
  ① 基础值   = 卡牌基础伤害 + ATK × 卡牌ATK系数
  ② 加法修正 = ① + Σ(平坦加成: buff / 符文 / 装备)
  ③ 乘法修正 = ② × Π(1 + 各乘区)                                // 易伤、增伤、元素克制、符文乘区
  ④ 暴击     = ③ × (1 + K_CRIT_BASE + LUK × K_LUK_TO_CRITDMG)   // 若触发
  ⑤ 减伤     = ④ × (1 - DEF/(DEF + K_DEF_SOFTCAP))              // 递减曲线，永不免伤
  ⑥ 格挡     = ⑤ - Block（先扣格挡，溢出打生命）
  ⑦ 下限     = max(⑥, K_MIN_DAMAGE)                              // 保证永远能破防
```

**其他公式：**

```
闪避率      = min(AGI × K_AGI_TO_DODGE / (AGI + K_DODGE_SOFTCAP), K_DODGE_MAX)   // 硬上限（建议 ≤ 40%）
暴击触发    = min(CRIT, K_CRIT_MAX)                                              // 硬上限（允许必暴 build）
先手判定    = AGI 高者先行；同值时玩家优先
移动额外距离 = floor(AGI / K_AGI_PER_STEP)                                        // K 较大，最多 +2
掉落数量权重 = 基础权重表 × (1 + LUK × K_LUK_TO_DROP)
稀有度提升   = 每 K_LUK_PER_RARITY 点 LUK，掉落稀有度检定 +1 次（取最好结果）
```

> ⚠️ **强数值养成的最大陷阱**：数值膨胀会让卡牌选择失效（无论出哪张牌都能一击必杀）。**防线是把卡牌伤害系数化（§7.5）**：卡牌不写"造成 12 伤害"，而写"造成 ATK×1.2 伤害"。这样 ATK 翻倍时，**所有卡牌一起翻倍，卡牌之间的相对优劣不变**，策略层不被数值冲垮。**这是本设计中不可妥协的一条。**

### 4.5 属性上限与软墙

- 每个属性设**软上限**（超过后碎片吸收效率递减）与**硬上限**（防溢出/防除零）。
- 软上限随层数解锁上移 → 制造"这层能吃的碎片是有意义的"节奏感。
- 数据放在 `AttributeCurveData` 资源里，策划可直接调曲线。

## 5. 装备系统（3 槽位）

### 5.1 槽位与设计分工

| 槽位 | 主要提供 | 主要改写 | 设计定位 |
|---|---|---|---|
| **武器 Weapon** | ATK、CRIT | **攻击范围与攻击形状**（决定你怎么打） | 定义 build 的"输出方式" |
| **盔甲 Armor** | HP、DEF | **受击时的规则**（反击、格挡转化、免疫） | 定义 build 的"生存方式" |
| **饰品 Trinket** | AGI、LUK、任意 | **资源规则**（体力、抽牌、卡组操作） | 定义 build 的"节奏" |

> **武器决定射程，这是必须的**：否则六边形战场上"我该站哪"这个问题没有变量。开局给的初始武器同时定义了本局前期的战斗风格。

### 5.2 装备以卡牌形式呈现的机制

**装备是"锚卡"（Anchor Card）——它以卡牌形态陈列在角色面板的槽位上，但不参与抽牌。** 它的效果通过**被动属性 + 向卡组注入的衍生卡**体现。

```
拾取「烈焰长剑」（武器）
  ├─ 被动：ATK +X, 攻击附带 1 层【燃烧】
  ├─ 攻击范围覆写：射程 1，命中目标及其后方 1 格（穿刺）
  └─ 注入卡组：《烈焰斩》×1（衍生卡，随装备卸下而移除）
```

> **为什么装备不进卡组（不需要抽到才能装备）**：会造成"抽不到装备就打不出输出"的卡手灾难，且与"3 槽位常驻"的体感冲突。

### 5.3 装备替换规则

- 3 个槽位，**每槽只能装 1 件**。拾取同槽位装备 → 弹出对比面板（新 vs 旧），选择替换或丢弃。
- 被替换的装备**直接销毁**（不做背包管理），其注入的衍生卡**立即从卡组/手牌/弃牌堆中移除**。
  - 理由：肉鸽单局内不该有仓库管理负担（以撒没有背包是对的）。
- 装备有**稀有度**（普通/精良/稀有/史诗/传说），稀有度影响：属性档位数量 + 是否带"规则改写"词条 + 注入卡的强度。
- **词条系统**：`base_stats`（固定）+ `affixes`（随机词条，数量由稀有度决定）→ 制造暗黑破坏神式的"这把词条好"的兴奋点，服务"强数值养成"。

### 5.4 装备强化（服务强数值养成）

- 局内可通过**营地房**或**商店**消耗金币为装备 **+1 强化**（提升 `base_stats`，不加词条）。
- 强化等级上限随层数提升。
- 这是金币在局内的主要消耗出口之一（§10.3）。

## 6. 符文系统（6 槽位 / 海克斯-小丑牌式）

> **D6 重新定义。** 符文**不是**属性词条集合，**不是**羁绊套装。符文是**《英雄联盟》海克斯强化 + 《小丑牌》小丑卡**式的**独立加成牌**：每张自己做一件明确的怪事，玩家把它们摆在一起，**组合是玩家自己研究出来的，游戏不提供"该凑什么"的提示表**。

### 6.1 设计定位

| | 装备（§5） | 符文（本章） |
|---|---|---|
| 回答的问题 | 我打多痛、扛多久 | **我这局在玩什么** |
| 变化频率 | 一局换 3–8 次 | 一局获得 6–12 个，槽位常在取舍 |
| 效果性质 | 数值 + 少量规则 | **规则改写为主**（≥70%） |
| 玩家心理 | "这把词条不错" | **"等等……这两个放一起是不是能无限连？"** |

**核心设计目标：让玩家在论坛/群里互相交流"我发现了一个组合"。** 这是《小丑牌》和《以撒》的长尾留存来源，也是本系统存在的唯一理由。

### 6.2 槽位结构

**6 个完全平等的槽位，有序排列。开局即全部开放（不做逐层解锁）。**

```
 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐
 │ 1  │ │ 2  │ │ 3  │ │ 4  │ │ 5  │ │ 6  │
 │符文│ │符文│ │ 空 │ │ 空 │ │ 空 │ │ 空 │
 └────┘ └────┘ └────┘ └────┘ └────┘ └────┘
   ← 触发结算顺序：1 → 2 → 3 → 4 → 5 → 6 →
```

| 规则 | 说明 |
|---|---|
| **槽位数** | 固定 6，**开局全开** |
| **槽位类型** | **无类型限制**，任何符文可放任何槽 |
| **顺序有意义** | 同一时机的多个符文，按**槽位序号 1→6** 依次结算（§6.5） |
| **可自由重排** | **战斗外任意时刻**可拖动重排、查看（战斗中锁定） |
| **满槽时获取新符文** | 三选一界面 → 选择覆盖某个槽位，或放弃。被覆盖的符文销毁 |

> **为什么开局全开、不做逐层解锁？**
> v0.1 的"逐层解锁槽位"是为了解决"6 个空槽看起来很空"。但《小丑牌》开局就是 5 个空槽，玩家反而立刻开始规划。**空槽是邀请，不是缺失。** 而且全开让玩家能从第 1 层就开始试组合，直接服务 D6 的核心目标。
> 层 Boss 的奖励改为：**三选一符文（保底 1 个稀有）+ 卡组容量 +1~2 + 一次性大奖励**（§9.8）。

### 6.3 统一触发时机表（符文互相咬合的地基）

**这是整个符文系统能产生涌现组合的技术前提。** 所有符文（以及装备、状态）的触发都必须挂在下面这张**共享**的时机表上。只要时机是共享的，组合就会自己长出来——不需要任何标签系统。

| 时机 | 说明 |
|---|---|
| `ON_BATTLE_START` / `ON_BATTLE_END` | 战斗开始 / 结束 |
| `ON_ROUND_START` / `ON_ROUND_END` | 回合开始 / 结束 |
| `ON_CARD_PLAYED` | 打出任意卡（可按 `card_type` / `tag` / `cost` 过滤） |
| `ON_CARD_DRAWN` / `ON_CARD_DISCARDED` / `ON_CARD_EXHAUSTED` | 抽 / 弃 / 消耗 |
| `ON_DECK_RESHUFFLED` | **弃牌堆洗回抽牌堆**（D2 带来的新时机，是很好的组合钩子） |
| `ON_ENERGY_SPENT` / `ON_ENERGY_LEFTOVER` | 消耗体力 / 回合结束剩余体力 |
| `ON_ATTACK` / `ON_HIT` / `ON_CRIT` / `ON_KILL` / `ON_OVERKILL` | 攻击链各节点 |
| `ON_TAKE_DAMAGE` / `ON_BLOCK_GAINED` / `ON_BLOCK_BROKEN` / `ON_DODGE` | 受击链各节点 |
| `ON_MOVE` / `ON_MOVE_ENEMY` / `ON_ROTATE` | 位移链（自己移动 / 推拉敌人 / 转向） |
| `ON_STATUS_APPLIED` / `ON_STATUS_TICK` / `ON_STATUS_EXPIRED` | 状态链 |
| `ON_TERRAIN_CHANGED` / `ON_ENTER_HAZARD` | 地形链 |
| `ON_ROOM_ENTER` / `ON_ROOM_CLEAR` / `ON_FLOOR_CLEAR` | 局内地图链 |
| `ON_SHARD_ABSORBED` / `ON_CARD_ACQUIRED` / `ON_GOLD_GAINED` | 局内成长链 |

**设计要求：每个时机至少要有 3 个符文能触发它，且至少有 1 个符文能"制造"它。** 这样才有"生产者—消费者"式的组合。

```
组合示例（这些不写在游戏里，是玩家自己发现的）：

  A《回声》     ON_DECK_RESHUFFLED → 抽 2 张牌
  B《薄纸卡组》 规则改写：卡组容量 −3
  → B 让洗回频率翻倍 → A 变成强力抽牌引擎。玩家自己发现"减少卡组是好事"。

  C《余烬》     ON_ENERGY_LEFTOVER → 每点剩余体力造成 ATK×0.3 伤害
  D《沉重》     规则改写：所有卡费用 +1，体力上限 +4
  → D 单看是负面，但配 C 就变成大范围收割。

  E《碾压者》   ON_MOVE_ENEMY → 被推动的敌人受到 ATK×0.5
  F《巨化》     规则改写：你的体型变为 6 格，无法被位移
  → F 让你堵住通路，敌人被迫贴身 → E 的推拉更容易命中多目标。
```

### 6.4 符文分类与占比目标

| 类别 | 说明 | 示例形态 | 占比目标 |
|---|---|---|---|
| **规则改写型** | 改变游戏的基础规则。**这是符文的主体** | 「每回合第一张卡费用为 0，但手牌上限 −2」/「你不再抽牌，改为每回合手牌固定为抽牌堆顶 4 张」/「你的体型变为 6 格」 | **35%** |
| **触发器型** | 挂在 §6.3 某个时机上，产出某种效果。**组合的主要材料** | 「你每移动 3 格，下一次攻击附加一次追击」/「洗回卡组时，获得 1 点体力」 | **30%** |
| **条件增益型** | 满足某状态时给强增益 | 「当你满血时，暴击率翻倍」/「当抽牌堆为空时，你的伤害 ×1.5」 | 15% |
| **乘区型（稀有）** | 直接提供伤害/格挡乘区。**故意做得稀有且醒目**，让"找到乘区"成为追求（Balatro 的 ×Mult 心理） | 「伤害 ×1.4」 | **≤8%** |
| **诅咒型** | 强正面 + 强负面。服务以撒式"破坏平衡"快感 | 「ATK ×2，但你无法获得格挡」/「体力上限 +3，但每回合失去 5% 最大生命」 | 12% |

**明确不做的类别：**
- ❌ 纯数值符文（「ATK +10%」）：占比压到 **0**。这种符文只会让玩家"拿数值最高的那个"，选择是假的，且完全不服务 D6。数值成长交给属性碎片和装备。
- ❌ 羁绊 / 标签计数 / 套装加成：**D6 已明确取消**。理由见 §6.7。

### 6.5 符文顺序与结算（Balatro 式的免费深度）

**同一时机被多个符文监听时，按槽位 1→6 顺序结算。**

```
槽1《锐化》   ON_ATTACK → 本次伤害 +ATK×0.5   (加区)
槽2《倍化》   ON_ATTACK → 本次伤害 ×1.5        (乘区)

顺序 [锐化, 倍化] → (base + 0.5ATK) × 1.5    ← 更好
顺序 [倍化, 锐化] → base × 1.5 + 0.5ATK
```

| 规则 | 说明 |
|---|---|
| 结算顺序 | 严格按槽位序号 1→6 |
| UI 要求 | **必须在符文面板上明示"结算顺序 →"的方向指示**，否则玩家不会意识到顺序有意义 |
| 重排时机 | 战斗外自由拖动；战斗中锁定（防止逐次操作反复调优，破坏节奏） |
| 教学 | 需要一个明确的教学时刻（第 2 层左右，玩家拿到第 2 个符文时）提示"顺序会影响结算" |

> 这一层深度是**免费**的：不需要额外内容，只需要一个稳定的结算顺序 + 清晰的 UI。而它能让"同样 6 个符文"产出多种强度，极大延长研究寿命。

### 6.6 符文获取与替换

| 项 | 规则 |
|---|---|
| **获取来源** | 层 Boss（保底，三选一含 1 稀有）、精英怪、宝藏房、商店、事件 |
| **获取形式** | **三选一**（海克斯式），选定即锁 |
| **槽满处理** | 三选一界面下方显示当前 6 槽，玩家指定覆盖目标；也可**全部放弃** |
| **被覆盖的符文** | 销毁，不可回收 |
| **重排** | 战斗外自由（§6.5） |
| **稀有度** | 普通/稀有/史诗/诅咒。稀有度影响效果强度与"规则改写"的激进程度 |

### 6.7 为什么取消羁绊系统（设计记录）

v0.1 曾设计"同标签 2/4/6 触发羁绊加成"。**D6 已取消**，理由记录如下，避免以后又被加回来：

| 羁绊系统的问题 | 说明 |
|---|---|
| **它把研究变成查表** | 羁绊表一旦公布，"研究打法"就退化为"凑齐 6 个火焰"。玩家不再思考机制，只数标签。这与 D6 的目标（玩家自己研究）直接相反 |
| **它压缩了组合空间** | 有羁绊时，跨标签组合几乎永远是错的（因为拿不到套装加成）。6 槽的组合数从 C(N,6) 塌缩为"几个预设流派" |
| **它抢走了符文自身的设计空间** | 符文一旦要背标签，设计师会倾向于让同标签符文互相配合 → 符文变得同质化，失去"每张做一件怪事"的性格 |
| **它不需要存在** | §6.3 的**共享触发时机表**已经天然提供了组合性，且组合是**机制层面**的（真实咬合）而非**计数层面**的（虚假凑数） |

> 符文**仍然可以有标签**（`tags`），但标签只用于：掉落池加权（§10.2）、UI 筛选、图鉴分类。**标签不产生任何游戏内加成。**

## 7. 卡牌与卡组系统

### 7.1 卡牌分类

| 类型 | 说明 | 典型体力消耗 |
|---|---|---|
| **攻击 Attack** | 造成伤害，可能带位移/状态 | 1–3 |
| **守备 Guard** | 获得格挡 / 减伤 / 反击姿态 | 1–2 |
| **移动 Move** | 位移自身（含突进、闪现、换位、转向） | 0–1 |
| **技能 Skill** | 抽牌、加体力、施加状态、召唤、改地形 | 0–3 |
| **姿态 Stance** | 常驻状态，直到被替换（每次只能有 1 个姿态） | 1–2 |
| **衍生 Derived** | 由装备/符文/其他卡生成，通常带【消耗】 | 0–1 |
| **诅咒 Curse** | 负面卡，来自陷阱/诅咒符文/事件；无法主动打出或有惩罚 | — |

### 7.2 三张基石卡（Cornerstone Cards）

《攻击》《防御》《移动》——**永久存在于卡组，不可被移除**。

| 规则 | 说明 |
|---|---|
| **参与正常循环** | 与其他卡一样：抽牌堆 → 手牌 → 弃牌堆 → 洗回（D2 之后不需要特殊回收逻辑） |
| **不可移除** | 商店/事件的"移除卡牌"不能选中它们 |
| **不占卡组容量** | 不计入容量上限（§7.6），避免占用构筑空间 |
| **可被升级** | 通过营地/事件/天赋升级（如《攻击+》），仍是基石卡 |
| **英雄变体** | 每个英雄的 3 张基石卡中有 1 张被替换为专属变体（§4.2） |
| **保底数量** | 若某效果试图移除/消耗掉所有基石卡，**战斗结束时强制补回**，保证卡组永远有基础操作 |

> 设计理由：基石卡是"保底操作层"。有了它们，玩家**在小卡组中始终能抽到可用的基础动作**，不会陷入"手上全是情境卡只能空过"的挫败。

### 7.3 体力（Energy）

- 每回合恢复至 **5 点**（基础），**不累积**到下回合。
- 可通过饰品/符文/姿态修改上限。
- **移动也消耗体力**（关键）：让 5 点体力池比 StS 的 3 点更紧，因为你要在"走位"与"输出"之间分配。
- **战斗结束后进入无限体力状态**：可自由使用《移动》卡在房间内走动、拾取掉落、走到出口。此时体力 UI 显示为 ∞。
- 回合结束时**剩余体力清零**，但这本身是一个触发时机（`ON_ENERGY_LEFTOVER`），可被符文利用（§6.3 示例 C）。

> 实现上"无限体力"= `BattleState.phase == EXPLORE` 时 `energy_check` 直接返回 true，且不扣减。**不要**用"体力=9999"实现，否则会污染所有依赖体力值的符文效果。

### 7.4 ✅ D2：抽牌堆 / 弃牌堆 循环（杀戮尖塔式）

> **v0.1 的"打出即随机洗回卡组、手牌跨回合保留、无弃牌堆"机制已废弃。** 采用 StS 标准三段循环。这消除了 v0.1 的 R1 风险（抽牌不可控、立即重抽、卡手死锁、概率不可读）。

#### 7.4.1 三个牌堆

| 牌堆 | 说明 | 玩家可见性 |
|---|---|---|
| **抽牌堆 Draw Pile** | 战斗开始时由卡组洗混而成 | **内容可查看（乱序显示），顺序不可见** |
| **手牌 Hand** | 当前可打出的牌，上限 **10** | 完全可见 |
| **弃牌堆 Discard Pile** | 打出的牌、回合结束弃掉的手牌 | **内容完全可见** |
| （消耗区 Exhaust） | 带【消耗】的卡打出后进入，本场战斗不再出现 | 可查看 |

#### 7.4.2 完整流程

```
战斗开始：
  1. 卡组（基石卡 + 所有非基石卡 + 装备/符文注入的衍生卡）→ 洗混 → 抽牌堆
	 （使用 RNGService.deck，seeded）
  2. 结算 ON_BATTLE_START
  3. 抽 5 张（首回合抽牌数 = 每回合抽牌数）

每回合开始：
  1. 回合数 +1
  2. 结算 ON_ROUND_START（符文、姿态、状态）
  3. 状态 tick（按 StatusEffectData.tick_timing）
  4. 抽牌：抽 D 张（D 基础 = 5，可被英雄被动/符文/装备修改）
	 - 抽牌堆不足时：把弃牌堆洗混 → 成为新抽牌堆 → 触发 ON_DECK_RESHUFFLED → 继续抽
	 - 若抽牌堆与弃牌堆都空（极端情况）→ 停止抽牌，不报错
	 - 手牌达到上限 10 时停止抽牌（多余的牌**不抽出**，留在抽牌堆）
  5. 体力 = 体力上限（基础 5）

打出一张卡：
  1. 检查合法性（体力足够 + 目标合法）
  2. 支付体力 → 触发 ON_ENERGY_SPENT
  3. 从手牌移出 → 结算效果（走 ActionQueue）→ 触发 ON_CARD_PLAYED
  4. 归宿：
	 - 带【消耗】→ 消耗区（战斗结束后返回卡组）
	 - 否则     → **弃牌堆**

回合结束（玩家主动点击）：
  1. 结算 ON_ROUND_END（格挡清空等）
  2. **弃掉全部手牌** → 弃牌堆，每张触发 ON_CARD_DISCARDED
  3. 剩余体力 → 触发 ON_ENERGY_LEFTOVER → 清零
  4. 进入敌方阶段

战斗结束：
  1. 消耗区、抽牌堆、弃牌堆、手牌 全部归还卡组
  2. 清除所有战斗内临时状态
```

#### 7.4.3 D2 带来的设计红利

| 红利 | 说明 |
|---|---|
| **概率可推算** | 玩家能看弃牌堆、能算"我的《重击》还有几回合回来"→ 决策可归因，这是策略深度的地基 |
| **洗回是一个新的触发时机** | `ON_DECK_RESHUFFLED`（§6.3）。配合**小卡组**（§7.6，8–20 张），洗回每 2–4 回合就发生一次 → 成为符文组合的高频钩子。**这是 D2 + D3 组合出的独有设计空间，StS 本身很少用**（StS 卡组太大，一场战斗可能只洗 1–2 次） |
| **"回合结束弃手牌"制造紧迫感** | 逼迫玩家每回合用完资源，而不是囤牌 |
| **成熟的平衡经验可直接借用** | 抽牌数、手牌上限、费用曲线都有大量公开数据可参考，降低调参风险 |
| **消除 R1 风险** | v0.1 需要"下半区插回 + 弃置操作"等一堆补丁，现在全部不需要 |

#### 7.4.4 小卡组 + 弃牌堆的节奏特性（重要）

因为 D3（容量上限 8–20 张，加 3 基石卡 = 总 11–23 张），而每回合抽 5 张：

```
卡组 11 张，每回合抽 5 → 约 2.2 回合走完一轮，一场 4 回合的战斗会洗回 1–2 次
卡组 23 张，每回合抽 5 → 约 4.6 回合走完一轮，一场 5 回合的战斗约洗回 1 次
```

**设计后果（都是好的）：**
1. **高一致性**：玩家几乎每场战斗都能抽到自己的核心卡 → build 的爽感能稳定兑现，服务"强数值养成"。
2. **卡组膨胀的代价是可感知的**：多拿一张烂卡 = 核心卡回来变慢，玩家能直接体会到，让 D3 的容量取舍有实感。
3. **洗回钩子高频**：见上表。
4. ⚠️ **风险**：一致性太高可能让战斗变成"每回合重复同一套连招"，缺少变化。**缓解**：① 情境卡（对特定敌人/地形才强）占一定比例；② 敌人意图迫使玩家改变出牌顺序；③ 部分强卡带【消耗】。这一点需在 M0 实测（R1'）。

### 7.5 卡牌数值系数化（强制规范）

为了让强数值养成不冲垮策略层（§4.4 的警告），**所有卡牌数值必须写成系数形式**：

```gdscript
# ❌ 禁止
damage = 12

# ✅ 强制
damage = flat_value + stats[stat_ref] * stat_ratio
# 《重击》: flat=0, stat_ref="ATK", ratio=1.8, cost=2
# 《连刺》: flat=0, stat_ref="ATK", ratio=0.5, repeat=3, cost=1
```

同理：格挡 = `flat + DEF × ratio`，治疗 = `flat + maxHP × ratio`。

**例外**：状态层数（燃烧 2 层）、位移格数（移动 2 格）、抽牌数、体力数 —— 这些是**离散量，不随属性缩放**，它们正是策略层的锚点。

> 效果：ATK 从 10 涨到 200 时，玩家"该出哪张牌"的判断逻辑**完全不变**，但爽感翻 20 倍。

### 7.6 ✅ D3：卡组容量上限 + 替换制

| 规则 | 值 |
|---|---|
| 初始卡组容量 | **8 张**（不含 3 张基石卡） |
| 容量上限提升 | 每击杀层 Boss **+1 ~ +2**（上限约 20） |
| 满容量时拾取新卡 | 弹出替换界面：**装备新卡 → 销毁一张旧卡**，或**放弃新卡** |
| 未满容量时 | 直接加入（仍可选择放弃） |
| 衍生卡 | **不占容量**（由装备/符文动态注入，随来源移除） |
| 基石卡 | **不占容量**，不可移除 |
| 诅咒卡 | **占容量**，需商店/事件/特定符文才能移除 |
| 商店移除卡 | 可用（价格递增），用于清理诅咒或腾容量 |

> **为什么不学 StS 的无限膨胀 + 稀缺移除？**
> ① 容量上限让**每次拾取都是取舍而非收集**，决策更即时（以撒的道具槽体感）。
> ② 小卡组（11–23 张）概率更可控，配合 D2 产生"高一致性 + 高频洗回"的独特节奏（§7.4.4），这是本作与 StS 的差异化。
> ③ 玩家不需要理解"卡组稀释"这个抽象概念，容量数字直接摆在脸上。

### 7.7 卡牌升级

- 营地房 / 事件 / 特定商店可**升级**一张卡（`upgraded_version` 字段）。
- 升级 = 提升系数 / 降低费用 / 增加一个效果步骤，**不改变卡的定位**。
- 每张卡只能升级 1 次（v1），避免数值失控。

### 7.8 卡牌标签（仅用于检索与加权，不产生加成）

`火焰` `冰霜` `雷电` `流血` `毒` `位移` `格挡` `反击` `范围` `连击` `远程` `近战` `消耗` `姿态` `诅咒` `衍生` `英雄专属`

标签服务：掉落池权重（§10.2）、UI 筛选、图鉴分类、**符文触发条件的过滤器**（如「打出【火焰】牌时…」——注意这是符文自己声明的条件，不是标签计数系统）。

## 8. 战斗系统（六边形战场 + 体型系统）

### 8.1 战场规格与坐标系

- 房间尺寸：**7 列 × 7 行 = 49 个六边形格**。
- 六边形朝向：**尖顶（Pointy-top）**，采用 **odd-r 偏移坐标**（奇数行右移半格）——让 7×7 在视觉上接近一个方正的地牢房间。
- **对外（策划/存档）坐标**：`(col, row)`，**1-indexed，原点在左下角**。玩家出生点 = **(4, 1)**（底边正中）。
- **对内（引擎/算法）坐标**：立方坐标 `Vector3i(x, y, z)`，`x+y+z == 0`。所有距离、射线、范围、旋转、**体型 footprint 变换**运算**必须在立方坐标下进行**（偏移坐标做这些运算会出错）。

```gdscript
class_name HexCoord
## 唯一的坐标转换出口，禁止在别处手写转换

# odd-r 偏移 (1-indexed, 左下原点) -> 立方
static func offset_to_cube(col: int, row: int) -> Vector3i:
    var c := col - 1
    var r := row - 1
    var x := c - (r - (r & 1)) / 2
    var z := r
    return Vector3i(x, -x - z, z)

static func cube_to_offset(cube: Vector3i) -> Vector2i:
    var col := cube.x + (cube.z - (cube.z & 1)) / 2 + 1
    var row := cube.z + 1
    return Vector2i(col, row)

static func distance(a: Vector3i, b: Vector3i) -> int:
    return maxi(absi(a.x - b.x), maxi(absi(a.y - b.y), absi(a.z - b.z)))

const DIRS := [                      # 6 个方向，索引即"朝向 0-5"
    Vector3i(1,-1,0), Vector3i(1,0,-1), Vector3i(0,1,-1),
    Vector3i(-1,1,0), Vector3i(-1,0,1), Vector3i(0,-1,1),
]

# 绕原点顺时针旋转 60° × steps —— 体型 footprint 旋转的基础
static func rotate(cube: Vector3i, steps: int) -> Vector3i:
    var v := cube
    for _i in range(posmod(steps, 6)):
        v = Vector3i(-v.z, -v.x, -v.y)
    return v
```

> **注意**：`(4,1)` 出生、敌人生成在上半区（row 4–7），形成"我方在下、敌方在上"的天然对峙感，让"射程"这个概念立刻有意义。

### 8.2 ✅ D8：体型系统（1 格 / 3 格 / 6 格）

**体型是所有单位（英雄、普通怪、精英、Boss）的通用属性，不是巨人的特例。**

#### 8.2.1 三种基准体型

`footprint` 定义为**相对锚点的立方坐标偏移数组**，配合 `facing` 旋转。三种基准体型均为**六边形三角形**，因此旋转规则统一、视觉一致：

| 体型 | 代号 | 格数 | 形状 | 相对偏移（facing=0 时） | 典型使用者 |
|---|---|---|---|---|---|
| **小型** | `S` | **1** | 单格 | `[(0,0,0)]` | 骑士、法师、弓箭手、多数杂兵 |
| **中型** | `M` | **3** | 边长 2 的三角形 | `[(0,0,0), (1,-1,0), (1,0,-1)]` | **巨人**、狼群头目、骑乘单位、多数精英 |
| **大型** | `L` | **6** | 边长 3 的三角形 | `[(0,0,0), (1,-1,0), (1,0,-1), (2,-2,0), (2,-1,-1), (2,0,-2)]` | **层 Boss**、少数超大精英 |

```
        小型 S (1格)        中型 M (3格)          大型 L (6格)

           ⬢                  ⬢ ⬢                  ⬢ ⬢ ⬢
                               ⬢                    ⬢ ⬢
                                                     ⬢
      占 49 格的 2%        占 49 格的 6%         占 49 格的 12%
```

> **选用三角形而非直线/菱形的理由**：① 三角形在六边形网格上是最紧凑的多格形状，视觉上像"一坨"而不是"一串"，符合"大块头"的直觉；② 边长 2 与边长 3 的三角形是同一族形状，旋转/碰撞代码完全共用；③ 三角形有明确的"尖端"，天然指示朝向，与 §8.2.3 的朝向系统完美咬合。
>
> `footprint` 是**数据字段**（`Array[Vector3i]`），所以以后要加 2 格直线、7 格花瓣等异形只需加数据，不改代码。

#### 8.2.2 体型的游戏机制后果

体型不是视觉装饰，它必须在**至少 6 个机制点**上产生真实差异，否则 D8 只是美术需求：

| 机制点 | 规则 |
|---|---|
| **1. 通行与卡位** | 移动时**所有 footprint 格必须同时合法**（非 WALL / 非 PIT / 未被其他单位占据）。→ **大型单位无法进入狭道**。这是体型最重要的战术后果 |
| **2. 命中与被命中** | 任意一格被范围覆盖即算命中（每次攻击只结算 1 次伤害，不因占多格而多次受伤）。→ **大体型更容易被 AOE 命中**，这是它的核心弱点 |
| **3. 攻击范围起点** | 射程从**最近的己方 footprint 格**起算。→ 大体型的"有效射程"更长 |
| **4. 位移抗性** | `knockback_resist` 默认与体型挂钩：S=0, M=1, L=完全免疫。→ 推拉流对大体型无效，需要改用其他手段 |
| **5. 旋转成本** | 多格单位改变 `facing` 会改变占位 → **转向本身需要目标格合法**，且可设为需消耗行动/体力（`rotate_cost`）。这让 M/L 单位"转身慢"，绕后打它们更有价值 |
| **6. 碾压 / 挤压** | 特定单位（巨人被动、部分 Boss）可穿过**比自己小的**单位所在格，被穿过者受伤并被挤到相邻空格；无空格则额外受伤留在原地 |
| **7. 地形交互** | 大型单位可"压碎"`RUBBLE`；可同时站在多个 hazard 上（**每个 hazard 各结算一次**，这是大体型的真实代价） |
| **8. 掉落散布** | 体型越大，死亡后掉落散布的格数越多（视觉上"爆一堆" ——服务 §10 的正反馈） |

#### 8.2.3 朝向（Facing）

| 项 | 规则 |
|---|---|
| 取值 | `0–5`，对应 `HexCoord.DIRS` |
| 背击 | 从"朝向的背面 2 个方向"攻击 → 伤害乘区加成 + **无法被闪避** |
| 玩家转向 | 通过《移动》类卡牌的位移自然改变；也有专门的低费"转向"卡 |
| 敌人转向 | 行动后自动转向其攻击/移动目标；**转向结果在意图中预告** |
| 多格单位转向 | 会改变占位，需目标格合法（见上表机制点 5） |
| UI | 单位脚下显示朝向扇形指示器；背面 2 格用不同颜色高亮 |

> **朝向 + 体型的乘法效应**：一个 6 格 Boss 转身需要一大片空地，玩家可以通过"把它逼到墙角"让它转不过身，然后一直站在它背后。这类**由规则涌现出的战术**正是我们要的东西。

#### 8.2.4 出生点与体型

玩家在 `(4,1)` 出生，`facing = 2`（朝上）：

| 体型 | 实际占据格（offset 坐标） |
|---|---|
| S | `(4,1)` |
| M | `(4,1)` + 2 格（朝上方向的三角形） |
| L | `(4,1)` + 5 格 |

> **约束**：`RoomLayoutData` 必须保证出生区域（`(4,1)` 及其上方 2 排的中央区域）**始终是可通行的空地**，否则 M/L 英雄无法出生。这是地形模板设计的硬性规则，**必须加进模板校验器**（§17-M0）。

### 8.3 格子（Cell）与单位（Unit）

**格子属性：**

| 字段 | 说明 |
|---|---|
| `terrain` | `FLOOR` / `WALL`(不可通行不可穿射) / `PIT`(不可通行可穿射) / `RUBBLE`(可通行，移动消耗+1；L 型可压碎) |
| `hazard` | 危害地面：`SPIKES` / `FIRE` / `POISON_CLOUD` / `ICE`(滑行) / `NONE`，带剩余回合数 |
| `feature` | 交互物：`CHEST` / `ALTAR` / `BRAZIER` / `EXIT_GATE` / `NONE` |
| `occupant_id` | 占据该格的 Unit id（尸体不占格） |
| `elevation` | v1 保留字段不启用（未来做高低差/远程加成） |

**单位属性：**

| 字段 | 说明 |
|---|---|
| `anchor: Vector3i` | 锚点立方坐标 |
| `size_class: SizeClass` | `S` / `M` / `L` |
| `footprint: Array[Vector3i]` | 相对锚点的偏移（facing=0 时）；实际占格 = `anchor + rotate(offset, facing)` |
| `facing: int (0-5)` | 朝向 |
| `stats: Dictionary` | 6 属性的当前值（含 buff 修正后） |
| `block: int` | 格挡，回合结束清空（骑士除外） |
| `statuses: Array[StatusInstance]` | 状态效果实例 |
| `team: int` | 0=玩家方，1=敌方，2=中立 |
| `knockback_resist: int` | 位移抗性（默认由 `size_class` 推导，可被覆写） |
| `rotate_cost: int` | 转向成本（S 通常为 0） |
| `intent: EnemyIntent` | 仅敌方，下回合行动预告 |

### 8.4 回合流程（状态机）

```
BattleStart
  ├─ 按 RoomLayoutData 生成地形 & 危害 & 交互物
  ├─ 校验出生区域对当前英雄体型合法（不合法则用备用模板）
  ├─ 生成敌人（§8.8，含体型合法性检查）
  ├─ 玩家单位放置于 (4,1)，facing=2，按体型展开 footprint
  ├─ 卡组洗混 → 抽牌堆（RNGService.deck）
  ├─ 结算 ON_BATTLE_START（符文/装备）
  ├─ 抽 5 张
  ├─ 按 AGI 决定先手方
  └─ 生成敌方首个 Intent 并显示
     ↓
┌──► RoundStart
│     ├─ 回合数 +1
│     ├─ ON_ROUND_START（符文按槽位 1→6 结算）
│     ├─ 状态 tick（燃烧/中毒等，按各自 tick_timing）
│     ├─ 抽 D 张（抽牌堆空 → 洗回弃牌堆 → ON_DECK_RESHUFFLED）
│     └─ 体力 = 体力上限
│        ↓
│    PlayerPhase  （玩家自由操作，无时限）
│     ├─ 打出卡牌（选目标 → 预览 → 确认 → 结算 → 入弃牌堆）
│     └─ 主动「结束回合」
│        ↓
│    RoundEndPlayer
│     ├─ ON_ROUND_END（格挡清空等）
│     ├─ 弃掉全部手牌 → 弃牌堆（每张触发 ON_CARD_DISCARDED）
│     └─ ON_ENERGY_LEFTOVER → 体力清零
│        ↓
│    EnemyPhase   （按 AGI 降序依次行动）
│     ├─ 每个敌人：执行已预告的 Intent
│     ├─ 执行后更新朝向（多格单位需校验占位合法）
│     └─ 生成下回合 Intent 并立即显示
│        ↓
│    RoundEndAll
│     ├─ 危害地面 tick & 衰减
│     ├─ 状态持续时间 −1 / 过期移除
│     └─ 检查胜负
│        ↓
└──── (未结束) 回到 RoundStart

BattleWin
  ├─ 三堆 + 消耗区 全部归还卡组，清除战斗内状态
  ├─ 掉落生成（卡牌 + 属性碎片 + 金币 + 可能的装备/符文），按体型散布在死亡位置
  ├─ 切换到 EXPLORE 阶段（无限体力）
  ├─ 玩家用《移动》卡走动拾取
  └─ 走到 EXIT_GATE → 返回房间图

BattleLose  → 结算界面 → 局外元进度奖励（精魄）
```

### 8.5 目标选择与范围形状

卡牌的作用范围由 `TargetSpec` 定义（数据驱动，不写死）：

| 形状 | 说明 |
|---|---|
| `SELF` | 自身（多格单位 = 全部 footprint 格） |
| `SINGLE(range)` | 单体，射程 `range`（从最近的己方 footprint 格起算） |
| `LINE(len)` | 直线，从自身朝某方向延伸 `len` 格（穿刺） |
| `CONE(len)` | 扇形，朝某方向的 60° 锥 |
| `BURST(radius)` | 以某点为中心的半径 `radius` 六边形圆 |
| `RING(radius)` | 以自身为中心的环（不含中心） |
| `ADJACENT_ALL` | 与自身 footprint 相邻的所有格（**多格单位的相邻格更多** → 大体型的 AOE 天然更大） |
| `TILE(range)` | 指定一个格子（用于位移、召唤、改地形） |

**视线（LoS）**：`WALL` 阻挡远程攻击。用立方坐标线性插值做射线检测（`cube_lerp` + 逐格采样）。多格单位：**任意一对 footprint 格之间有视线即算有视线**。

**预览是硬需求**：悬停卡牌 → 高亮所有合法目标格；悬停目标 → 高亮实际波及格（含多格单位的完整占位）+ **显示预计伤害数字（含暴击区间）**。没有这个，六边形战棋会让玩家极度困惑。

### 8.6 位移与推拉

| 类型 | 说明 | 多格单位处理 |
|---|---|---|
| **移动 Move** | 沿可通行格逐格移动 N 步（A* 寻路，路径可见） | 每一步都需全 footprint 合法 |
| **突进 Dash** | 直线冲向目标，撞到单位即停（可结算撞击伤害） | 同上 |
| **闪现 Blink** | 无视中间格直接到达目标格（可越墙） | 只校验终点 footprint |
| **击退 Knockback** | 目标沿"攻击者→目标"方向被推 N 格；撞墙/撞单位 → 停下并受额外伤害 | 受 `knockback_resist` 削减；L 免疫 |
| **拉拽 Pull** | 目标被拉向攻击者 | 同上 |
| **换位 Swap** | 与目标交换位置 | **仅同体型可换位**（否则占位无法互换） |
| **碾压 Trample** | 穿过比自己小的单位所在格，被穿过者受伤并被挤开 | 仅 M/L 可用 |
| **转向 Rotate** | 改变 facing | 多格单位需目标占位合法，可能有 `rotate_cost` |

> 位移必须能造成**伤害与地形交互**（推入尖刺、推入火焰、推入深坑、撞墙），否则位移卡只有"跑位"价值，太单薄。这是 Into the Breach 最重要的一课，也是 §6.3 中 `ON_MOVE_ENEMY` 能成为符文组合钩子的前提。

### 8.7 敌人意图预告（Intent）

**这是本作可读性的生命线。** 每个敌人在其行动前一整个回合就显示：

```
┌────────────────────────────┐
│  🗡 12   ← 图标 + 数值      │  攻击意图：显示预计伤害
│  ▓▓░░    ← 目标格高亮      │  红色高亮它将攻击的所有格子
│  →→      ← 移动预告        │  虚线箭头显示它将移动到哪
│  ↻       ← 转向预告        │  显示它行动后的朝向
└────────────────────────────┘
```

意图类型：`ATTACK`(带伤害值) / `MULTI_ATTACK`(N×D) / `BUFF` / `DEBUFF` / `SUMMON` / `MOVE` / `ROTATE` / `SPECIAL`(未知，用于 Boss 阶段) / `SLEEP`。

**关键规则：意图必须是承诺。** 敌人预告了打 `(4,1)`，即使玩家跑走了它也**打空**（或按明示规则重定向——规则必须固定且写在敌人图鉴里）。

- **近战敌人 = 打空**（可被走位躲开）
- **远程/施法敌人 = 追踪目标**（不可靠走位躲开，需要打断、格挡或断视线）

> 这个区分让"走位"与"硬吃"成为两种有效应对，制造敌人的多样性；也让"躲到墙后断视线"成为一个真实的战术选项。

### 8.8 敌人生成规则

- 房间的敌人组合来自 `EncounterData`（**手工设计的怪物组模板**），而非纯随机拼凑 —— StS 的经验：手工设计的组合远比随机组合有趣。
- 生成位置：`EncounterData` 定义**生成区域**（"上半区"、"贴墙"、"随机 3 格"），在区域内 seeded 随机。
- **硬约束**：
  - 敌人不得生成在距玩家出生 footprint `< 2` 格的位置
  - 全部 footprint 格必须合法（非 WALL / PIT / 已占据）→ **M/L 敌人需要连续空地，生成器必须做 footprint 合法性搜索**
  - 若某个 M/L 敌人在当前地形模板上找不到合法位置 → 按 `EncounterData.fallback` 降级为更小体型的替代怪，或换模板（**生成器必须有降级路径，不能死循环**）
- 房间进入时播放约 0.5s 的"敌人落地"演出，让玩家读取战场。

### 8.9 状态效果框架

统一数据驱动，不为每个状态写独立脚本。

| 字段 | 说明 |
|---|---|
| `id` | `burn` / `poison` / `bleed` / `weak` / `vulnerable` / `stun` / `root` / `chill` / `strength` … |
| `stack_mode` | `STACK`(层数叠加) / `REFRESH`(刷新时长) / `INDEPENDENT`(独立计时) |
| `tick_timing` | `ROUND_START` / `ROUND_END` / `ON_HIT` / `NONE` |
| `decay` | 每回合层数变化（燃烧 −1，力量 0） |
| `modifiers` | 对属性/乘区的修正（易伤 → 受伤乘区 +X%） |
| `on_apply / on_tick / on_remove` | 效果步骤数组（复用 §15.3 的 `EffectStep`） |
| `is_debuff` | 用于"净化"类效果筛选 |
| `max_stack` | 层数上限 |

必备基础状态（v1）：`力量`(增伤) `敏锐`(增格挡) `虚弱`(降伤) `易伤`(受伤增) `燃烧` `中毒` `流血` `眩晕`(跳过行动) `定身`(不可移动) `护盾`。

### 8.10 胜负判定

- **胜利**：敌方全部单位死亡，或满足 `EncounterData.win_condition`（"存活 5 回合"、"到达出口格"、"保护目标"）。
- **失败**：玩家单位 HP ≤ 0 → 本局结束。
- **无平局 / 无逃跑**（v1）：逃跑机制会破坏"清房间"的节奏闭环。若后续需要，作为特定卡牌/符文能力提供。

## 9. 关卡与地图系统（盲探式爬塔）

### 9.1 整体结构

```
塔（一局）
 └─ 章 Act ×3          （每章独立主题：视觉、怪物池、卡池权重、地形规则）
     └─ 层 Floor ×3    （共 9 层 + 终章 Boss 层 = 10 层）
         └─ 房间 Room ×3~9   （Boss 房位置未知）
```

| 层 | 房间数 | 说明 |
|---|---|---|
| 第 1 层 | 3 | 教学节奏，房间少，快速给到第一批卡与符文 |
| 第 2–3 层 | 4–5 | |
| 第 4–6 层 | 5–7 | |
| 第 7–9 层 | 7–9 | |
| 终章层 | 1（纯 Boss） | 最终 Boss，多阶段，L 体型 |

- **每层必有一个层 Boss**（第 3/6/9 层为章 Boss，更强、掉落更好）。
- 击杀层 Boss → 层结算界面（§9.8）→ 进入下一层。

### 9.2 层内房间图生成

采用**加权无向图**（而非 StS 的有向层图），因为 D4 要求"探索并找到 Boss"：

```
生成算法（seeded, RNGService.map）：
1. 确定房间数 N（按层查表 + 少量随机）
2. 生成 N 个节点，用「随机生成树 + 少量额外边」连接
   → 保证连通，且存在少量环路（环路让回头路有意义，也让盲探不会变成单线走廊）
3. 选一个节点为【入口】（玩家起点，已探明）
4. 选【Boss 房】：
   ⚠️ 硬约束（D4/D5 的必要配套，见 §9.5）：
      图距离(入口, Boss房) >= max(2, ceil(N/2))
   在满足约束的节点集合中随机选一个
5. 按配额分配其余房间类型（§9.6），满足约束：
   - 入口相邻至少 1 个【普通战斗房】（防止开局撞精英）
   - Boss 房相邻至少 1 个【营地房】（打 Boss 前允许休整 —— 重要的体验保障，
     且在盲探下它同时是"你快到了"的隐性信号，见 §9.3.2）
   - 【商店】【营地】每层至多 1 个
   - 【精英】数量随层数上升
6. 走廊（边）上按概率生成【走廊事件】（陷阱/伏击/小宝箱），借鉴暗黑地牢的走廊
7. 为每个房间预生成 (RoomLayoutData, EncounterData) 配对并校验体型可行性（§8.8）
```

**UI 表现**：暗黑地牢式的地图面板 —— 节点 + 连线 + 迷雾，点击相邻已连通节点移动。

### 9.3 ✅ D4：盲探迷雾（Boss 房不可见）

**玩家不知道哪个房间是 Boss 房。必须靠探索找到。**

#### 9.3.1 可见性规则

| 房间状态 | 显示内容 |
|---|---|
| **已进入（已探明）** | 完整显示：房间类型图标 + 是否已清空 + 掉落是否已拾取 |
| **相邻未探明** | 只显示**节点存在 + 连线**，图标为 `?`。**不显示类型，不显示危险等级** |
| **远处未探明** | 只显示节点存在 + 连线（`?`），可能连线也未知（见下） |
| **未知连线** | 从未探明节点延伸出去的边：**不显示**。玩家只能看到"已探明节点的邻边"。→ 地图是逐步展开的，而不是一开始就给你完整拓扑 |
| **Boss 房** | **与其他未探明房间完全无区别**，也是 `?`。进入后才知道 |

> **与 v0.1 的关键差异**：v0.1 让 Boss 房始终可见（理由是"让决策基于信息"）。**D4 明确否决了这一点**，理由是探索的紧张感来自信息缺失——这是《暗黑地牢》和《以撒》的做法，也是本作 P3 支柱（探索是赌博）的核心。
>
> 这个改动把"什么时候去打 Boss"的决策，从**路线规划**换成了**风险管理**：你不知道下一扇门后面是 Boss 还是精英，所以你必须**始终保持能打 Boss 的状态**——不能把血和资源花光。这是一种不同但同样有效（且更紧张）的决策形态。

#### 9.3.2 盲探的信息补偿（必须做，否则退化为纯运气）

**纯粹的信息真空会让探索变成随机点击。** 必须提供**间接线索**，让玩家能"推理"而不是"猜"。这是 D4 能否成立的关键：

| 线索 | 机制 | 玩家能推理出什么 |
|---|---|---|
| **① 声音/氛围线索** | 进入一个房间时，若**相邻**房间是 Boss 房，播放特殊音效 + 屏幕边缘微弱红光 + 地面震动 | "Boss 就在旁边某一间" —— 缩小到 1–3 个候选 |
| **② 营地锚点** | Boss 房必邻 1 个营地房（§9.2 约束 5）。玩家发现营地时 → 得知 Boss 在营地的邻居中 | 强线索，且天然让"找到营地"变成好事 |
| **③ 图距离提示** | 地图面板显示"已探明 X / N 个房间"。Boss 房的图距离约束（≥ ceil(N/2)）**写在图鉴里**，玩家可自行推理 | 排除靠近入口的节点 |
| **④ 探明后的拓扑** | 每探明一个房间就揭示它的所有邻边 → 玩家逐步看清图结构，能识别"死角节点" | Boss 常在图的远端 |
| **⑤ 可购买/掉落的透视道具** | 商店/事件/符文可提供「揭示本层 1 个随机未探明房间的类型」或「揭示 Boss 房位置」 | **让"我想知道"变成一个有价格的需求** —— 这是把信息变成资源的标准手法 |
| **⑥ 敌人强度回声** | 层内房间的敌人强度随"图距离入口"轻微上升 | 打得越难 = 越接近远端 = 越可能接近 Boss |

> **⑤ 特别重要**：它把 D4 造成的信息缺失变成了**一个新的经济需求**。玩家会开始在商店里权衡"买一张卡还是买一次透视"，这是纯增益。

#### 9.3.3 盲探的兜底保护（防止不可接受的挫败）

| 风险 | 保护措施 |
|---|---|
| 残血时误入 Boss 房 → 秒死，感觉不公平 | **进入 Boss 房时不立即开战**：先显示一个"沉重的门 / Boss 剪影"的确认界面，玩家可选择「进入」或「暂时离开」。离开不消耗腐蚀度。→ **发现 Boss 房 ≠ 被迫打 Boss**。这条是 D4 + D5 组合下的必要安全阀 |
| 残血时误入精英房 | 同上机制的弱化版：精英房进入前给一次"你感到强烈的压迫感"提示 + 确认。普通战斗房**不给**确认（否则探索没有风险） |
| 把全层探完还没找到 Boss | 不可能发生（Boss 必存在于图中），但 UI 要显示"已探明 X/N"让玩家知道还剩几间 |
| 探完全层才找到 Boss，腐蚀度爆表 | 这是玩家的选择结果，不保护。但 §9.4 的腐蚀度收益必须足够高，让"探完全层"是一条**可行的通关路线**而非陷阱 |

### 9.4 腐蚀度（Corruption）—— 探索的风险回报轴

> 对《暗黑地牢》"火把/光照"的改造。在 D4/D5 之后它的作用更重要了：**这是唯一让"多探一间房"产生显式代价的机制**。

| 规则 | 说明 |
|---|---|
| **累积** | 每**进入并清空**一个新房间，本层腐蚀度 +1（精英房 +2）。**进入 Boss 房后选择离开不 +1**（§9.3.3） |
| **每层重置** | 进入新层时归零（但基线随层数上升） |
| **负面** | 腐蚀度每 +1：敌人 HP/ATK 提升一档；每 +3：怪物组难度档位 +1。**对 Boss 同样生效** |
| **正面** | 腐蚀度每 +1：掉落数量/稀有度权重提升；每 +3：额外掉落一次属性碎片 |
| **UI** | 层内常驻显示腐蚀度条，且**明示"若现在遇到 Boss，它会强化多少"**（不能藏这个信息 —— Boss 位置可以藏，Boss 强度不能藏） |

**产生的决策（在 D4 盲探下的新形态）：**
- **保守打法**：探到 Boss 就打，Boss 弱但自己也弱（卡少、碎片少）
- **贪婪打法**：先绕开/离开 Boss 房，把全层刷完再回来，自己很强但 Boss 也很强
- **D4 带来的额外张力**：你**不知道**还要探几间才能碰到 Boss，所以"我要不要再推一扇门"这个决策每次都带着未知

> **两条路线都必须是可行的通关路线** —— 这是本机制成功的判据。

### 9.5 ✅ D5：不做 Boss 门解锁条件

**取消 v0.1 的"封印印记"机制。找到 Boss 房即可进入（经过 §9.3.3 的确认界面）。**

> **为什么 D4 + D5 能同时成立（而 v0.1 需要印记锁）？**
>
> v0.1 的印记锁是为了解决"Boss 房可见 → 玩家开局直奔 Boss → 跳过 90% 内容"。
> **D4 让 Boss 房不可见，这个问题从根上消失了**：你没法直奔一个你不知道位置的房间。想找到 Boss，你**必须探索**——探索本身就成了"锁"，而且是一把不需要额外规则解释的锁。
>
> 这是 D4 + D5 的协同：**用信息缺失代替资源门槛**。少一套系统，多一层紧张感。

**但必须保留两个约束，否则"运气好开局就撞到 Boss"会摧毁体验：**

| 约束 | 说明 |
|---|---|
| **① 图距离下限**（§9.2 步骤 4） | `图距离(入口, Boss房) >= max(2, ceil(N/2))`。保证玩家在遇到 Boss 前**至少经过若干房间**，有基本的成长 |
| **② 进入前确认**（§9.3.3） | 发现 Boss 房 ≠ 被迫开战。玩家可以先离开，去把这层刷强再回来 |

> 有了这两条，"撞到 Boss"永远是一个**机会**（我可以现在打，也可以晚点打），而不是一个**陷阱**。

### 9.6 房间类型

| 类型 | 内容 | 掉落 | 备注 |
|---|---|---|---|
| **普通战斗** | 1 个怪物组 | 卡牌 + 碎片 + 金币 | 主体内容。进入**不给**确认提示 |
| **精英战斗** | 高难怪物组（常含 M/L 体型） | 高品质卡 + 符文（三选一）+ 大量碎片 | 进入前给"压迫感"提示 + 确认 |
| **事件** | 文本三选一（借鉴 StS 事件） | 多样（含代价型） | 结果受 LUK 影响 |
| **商店** | 买卡/符文/装备/强化/移除卡/**透视道具** | — | 每层至多 1 |
| **宝藏** | 无战斗，1 个宝箱（可能有陷阱） | 装备 / 符文 | 可能需要"支付代价" |
| **营地** | 三选一：治疗 / 升级一张卡 / 重排符文并小额恢复 | — | 每层至多 1，**且必邻 Boss 房**（§9.2） |
| **Boss** | 层 Boss（多阶段，L 体型） | 三选一符文（保底 1 稀有）+ 层结算 | 进入前确认（§9.3.3） |
| **走廊事件** | 边上的小事件（陷阱、伏击、拾取） | 小额 | 借鉴暗黑地牢走廊 |

### 9.7 房间战场生成

同一个房间图节点 → 进入后生成一个 **7×7 六边形战场**：

```
战场生成 = RoomLayoutData（手工设计的地形模板库） + EncounterData（怪物组） + 随机点缀
```

`RoomLayoutData` 模板库必须包含以下几类（**其中"狭道"类是 D8 体型系统的必要配套**）：

| 模板类型 | 描述 | 服务的机制 |
|---|---|---|
| **空旷厅堂** | 无障碍 | 基准战场；对 L 型 Boss 友好 |
| **石柱大厅** | 4–6 根柱子（WALL）对称分布 | 断视线；限制 M/L 通行 |
| **狭道 / 门洞** | 中间一排 WALL 只留 1–2 格通道 | ⭐ **体型系统的核心舞台**：巨人堵门、L 型敌人无法通过 |
| **断桥** | 中间一排 PIT，分割上下战场 | 推入深坑；限制通行 |
| **尖刺牢房** | 随机 5–8 格 SPIKES | 推拉伤害；L 型同时踩多格的代价 |
| **熔炉** | 两侧 BRAZIER（可被推入 → 生成火焰区域） | 地形改造 |
| **环形回廊** | 中央一大块 WALL，四周环形通道 | 风筝流舞台；绕后 |

> **地形模板必须手工设计并与怪物组配对**（近战怪配开阔地、远程怪配掩体、L 型 Boss 配开阔地）。纯随机地形会产出大量"无聊"或"不可能"的战场。这是《Into the Breach》与《火焰纹章》的共同结论。

> **模板校验器（必做工具，§17-M0）**：每个模板需自动校验 ① 出生区对 S/M/L 三种体型均合法；② 全图连通（不存在无法到达的区域）；③ 可容纳其配对 `EncounterData` 中所有敌人的 footprint。

### 9.8 层结算（击杀层 Boss 后）

| 奖励 | 说明 |
|---|---|
| **三选一符文** | 保底 1 个稀有；这是符文的主要来源 |
| **卡组容量 +1 ~ +2** | §7.6 |
| **大额属性碎片** | 玩家可选择分配到哪个属性（一次定向成长的机会） |
| **属性软上限提升** | §4.5 |
| **完全恢复 / 大额治疗** | 进入下一层前的重置 |
| 本层统计 | 探明房间数、最终腐蚀度、获得卡数等 |

## 10. 掉落、经济与局内成长

### 10.1 掉落物类型

| 掉落物 | 拾取方式 | 作用 |
|---|---|---|
| **属性碎片 Shard** | **走过即自动吸收**，无需选择 | 6 种，对应 6 属性，立即永久提升本局属性 |
| **卡牌 Card** | 走上去 → 弹出确认/替换界面 | 加入卡组（受容量上限约束） |
| **金币 Gold** | 走过即自动拾取 | 商店 / 装备强化 / 事件支付 / 透视道具 |
| **装备 Equipment** | 走上去 → 对比替换界面 | 装备到对应槽位 |
| **符文 Rune** | 走上去 → 三选一/覆盖界面 | 装入符文槽 |

> ~~封印印记 Sigil~~ —— **D5 已移除**。

> 「属性碎片走过即吸收」是很好的设计：它让**战斗结束后的走动拾取变成一个持续的正反馈动作**（像以撒吃钱），而卡牌/装备/符文的"要不要换"决策集中在少数几次，不打断节奏。**保留这个分工。**

### 10.2 掉落生成规则

```
战斗结束 → 对每个死亡敌人计算掉落：
  1. 查 EnemyData.loot_table
  2. 数量检定：base_count × (1 + LUK × K) × (1 + 腐蚀度加成)
  3. 稀有度检定：LUK 每 K 点 → 多掷一次，取最好
  4. 卡牌池筛选：
     - 按当前【章】的卡池权重
     - 按【英雄专属标签】加权（保证英雄特色卡有出场率）
     - 按【玩家已装备符文/装备的标签】小幅加权
       ⚠️ 这一条在 D6 之后依然重要，但含义变了：不是为了凑羁绊，
          而是为了让玩家"正在尝试的方向"能拿到材料。
          加权幅度要小（建议 ≤ 1.3×），否则会削弱 D6 的自由探索感。
     - 排除已达 max_copies 的卡
  5. 掉落物按死亡单位的 footprint 散布（体型越大散布越广，§8.2.2）
```

### 10.3 局内经济出口

金币用途（必须多于 1 个，否则金币无决策）：
1. 商店购买卡牌 / 符文 / 装备
2. **装备强化 +1**（§5.4）
3. 商店移除卡牌（价格递增）
4. **透视道具**（§9.3.2-⑤）—— D4 带来的新出口
5. 事件中支付（贿赂、赎金、赌博）
6. 宝藏房开锁

### 10.4 局内难度曲线控制变量

策划可调的旋钮（放在 `DifficultyCurveData`）：

| 旋钮 | 说明 |
|---|---|
| `enemy_stat_curve[floor]` | 敌人属性基线随层数 |
| `corruption_step` | 腐蚀度每级的敌人/掉落变化幅度 |
| `boss_min_graph_distance[floor]` | Boss 房与入口的最小图距离（§9.2） |
| `deck_capacity[floor]` | 卡组容量上限 |
| `cards_drawn_per_turn` | 每回合抽牌数（基础 5） |
| `shard_yield[floor]` | 每层碎片总产出（决定玩家数值成长速度） |
| `rarity_weights[act]` | 各稀有度权重 |
| `size_class_weights[floor]` | M/L 体型敌人的出现比例随层数 |

## 11. 局外元进度（强数值养成）

> 「强数值养成」是明确诉求。但肉鸽的局外数值养成有个经典陷阱：**如果局外数值太强，前 20 小时的失败会被归因为"我练度不够"而非"我玩得不好"**，策略深度感会流失。
>
> 解决方案：**局外提供"选择的广度"，局内提供"数值的高度"。**

### 11.1 四条局外进度线

| 线 | 内容 | 提供什么 |
|---|---|---|
| **1. 英雄等级** | 消耗【精魄】提升等级 → 提升 **6 属性的初始基线** | **数值**（有上限、有软墙） |
| **2. 天赋树** | 每英雄独立的树，消耗【天赋点】解锁 | **规则**（如"开局多 1 个符文"、"基石卡《攻击》默认升级"、"卡组容量 +2"、"开局多 1 次透视"） |
| **3. 图鉴解锁** | 局内首次遇到 → 永久加入掉落池 | **广度**（卡池/符文池/装备池/怪物池扩容）。**符文图鉴尤其重要——它直接决定 D6 的组合空间大小** |
| **4. 难度阶层** | 通关后解锁「深渊 1~20」，每层叠加一条负面规则 | **长期挑战** |

### 11.2 货币

| 货币 | 获取 | 用途 |
|---|---|---|
| **精魄 Essence** | 每局结束按进度/击杀/层数结算（**失败也给**，约为通关的 40%） | 英雄等级 |
| **天赋点 Talent** | 成就 / 首次击杀 Boss / 通关 | 天赋树 |
| 金币 Gold | 局内 | 局内消耗（**不带出局**） |

> **失败也给精魄**是必须的：没有它，早期高失败率会让玩家感到"这一小时白玩了"。这是《哈迪斯》《死亡细胞》验证过的留存设计。

### 11.3 数值养成的天花板设计

- 英雄等级提供的属性加成走**明显的递减曲线**，并设硬上限（满级 ≈ 局内第 3 层的水准）。
- 目的：满级角色**依然需要靠局内碎片**才能通关，局内成长的爽感不被局外练度抢走。
- 局内单局的数值成长倍数目标：**开局 → 终局 ≈ 15–30 倍**（这是"强数值"的实际体感来源）。

### 11.4 难度阶层（追上 broken build）

我们在 §2.3 决定**不平衡掉 OP 组合**（这正是 D6 的目的）。那么必须有机制追上玩家：

```
深渊 1：敌人 HP +15%
深渊 2：+ 卡组容量上限 −2
深渊 3：+ 精英房数量 +1
深渊 4：+ 腐蚀度起始值 +2
深渊 5：+ Boss 获得一个额外机制
深渊 6：+ Boss 房最小图距离 +1（要探更多才能找到）
深渊 7：+ M/L 体型敌人比例提升
...
深渊 20：全部叠加 + 特殊终局 Boss
```

每层解锁需通关上一层。提供 100+ 小时长尾，且**不需要新内容**。

## 12. 架构纪律与联机底层预留

> **D7：不实现任何联机功能，不设计联机玩法。但技术底层要为它留门。**
>
> 好消息：下面 5 条纪律**对单人项目本身就是净收益**（可测试性、可回放、可复现 bug、Undo、战报）。**联机预留不是额外成本，而是这些纪律的副产品。**

### 12.1 五条架构纪律（v1 必须遵守）

#### 纪律 1：所有随机走注入式 RNG 服务

```gdscript
# ❌ 禁止在任何游戏逻辑中直接调用
randi() / randf() / Array.shuffle() / Array.pick_random()

# ✅ 必须
RNGService.map      # 地图生成（房间图、Boss 位置、房间类型）
RNGService.loot     # 掉落（数量、稀有度、卡池抽取）
RNGService.combat   # 命中、暴击、闪避、敌人 AI 随机选择
RNGService.deck     # 洗牌（战斗开始洗混、弃牌堆洗回）
RNGService.event    # 事件结果
```

单一主 seed 派生多条独立子流，各子流状态存入 `RunState.rng_states`。

**单人收益**：种子分享、录像回放、bug 精确复现、自动化测试可重复。
**联机预留**：主机广播 seed 即可。

#### 纪律 2：所有游戏状态变更必须经过 `ActionQueue`

卡牌效果、状态 tick、敌人行动、掉落结算 → 全部转成 `GameAction` 推入队列，由 `ActionResolver` 顺序执行并发出事件。

```gdscript
# ❌ 禁止
target.hp -= 20

# ✅ 必须
ActionQueue.push(DamageAction.new(source, target, damage_packet))
```

**要求**：`GameAction` 必须是**可序列化**的纯数据（这是联机预留的关键，也让存档/回放变简单）。

**单人收益**：完整操作日志 → 战报、回放、Undo（§13.2）、精确的 bug 报告。
**联机预留**：只需把队列的产生端改为"主机产生、全端重放"。**这是 5 条里最关键的一条。**

#### 纪律 3：表现层只订阅事件，绝不驱动逻辑

逻辑**瞬时算完**，表现层再按事件流播放动画。

```
ActionResolver 执行 → EventBus.damage_dealt.emit(payload) → unit_view 播动画
                                                          → damage_number 飘字
                                                          → audio 播音效
```

**铁律**：`src/core/` 中不允许出现 `await get_tree().create_timer()`、不允许引用任何 Node。逻辑不等待动画。

**单人收益**：战斗可在无渲染下跑完 → 单元测试 + AI 自动对战平衡验证（§17-M0 的 10 万次模拟依赖这条）；"跳过动画/快速模式"免费实现。
**联机预留**：网络延迟不影响逻辑一致性。

#### 纪律 4：战斗层按"单位集合"设计

`Unit` 是粒度，不假设我方只有 1 个单位。

**单人收益**：召唤物、宠物、被控制的敌人（"魅惑"效果）都免费支持——这是 R3 的备选方案。
**联机预留**：多个玩家单位不需要重写战斗层。

#### 纪律 5：逻辑完全确定性

给定 `(RunState, seed, 玩家输入序列)`，结果必须**逐位一致**。

| 要求 | 说明 |
|---|---|
| 禁止依赖 `Dictionary` / `Node.get_children()` 的遍历顺序做逻辑判断 | 需要顺序时用显式排序的 `Array`（如符文按槽位 1→6，敌人按 AGI 降序 + id 作为 tiebreak） |
| 禁止在逻辑中使用 `Time.get_ticks_msec()` / 系统时间 | |
| 浮点运算需注意 | 建议关键数值（HP、伤害）用 `int`，只在中间计算用 `float` 并明确 round 规则 |
| 符文触发顺序必须由槽位决定 | §6.5 —— 这条纪律和 D6 的顺序机制天然一致 |

**单人收益**：回放能对得上、种子能复现、玩家报 bug 时给种子就能重现。
**联机预留**：主机权威模型的前提。

### 12.2 代码层面的预留（不实现，只留位）

```
src/net/
├── net_stub.gd          # 空实现：is_multiplayer() -> false; is_host() -> true
└── README.md            # 记录：若做联机，改动点清单
```

**改动点清单（写进 README，供未来参考）：**

| 改动点 | 说明 |
|---|---|
| `ActionQueue` 的产生端 | 客户端发送 `GameAction` 意图 → 主机校验并广播已裁决的 `GameAction` 序列 |

### 13.2 UX 硬性要求（不可省略）

| 要求 | 理由 |
|---|---|
| **伤害预览**：悬停目标显示"预计伤害 X（暴击 Y）"，含所有 buff/debuff/符文计算 | 强数值 + 6 个符文叠加后玩家无法心算，没有预览 = 决策靠猜 |
| **抽牌堆 / 弃牌堆浏览器**：抽牌堆内容可查看（乱序），弃牌堆完全可见并显示顺序 | D2 的核心红利就是"概率可推算"，不给这个 UI 等于放弃 D2 的价值 |
| **符文面板必须明示结算顺序方向** | §6.5 —— 顺序机制若不可见等于不存在 |
| **符文详情必须写清触发时机** | D6 要求玩家能推理组合。符文描述必须精确到"何时触发、触发几次、与什么交互" |
| **体型轮廓描边**：所有单位按 footprint 完整描边，不只画在锚点格上 | 体型系统若不可读，玩家会一直误判"我能不能走进去" |
| **移动预览必须显示 footprint**：拖动移动时，实时显示落点的完整占位与是否合法 | M/L 单位的移动合法性无法靠直觉判断 |
| **敌人图鉴**：战斗中可查看敌人完整能力说明 + **意图是否可躲**（打空/追踪） | 意图图标信息量不足；"可不可躲"是核心决策信息 |
| **Undo（有限）**：位移/转向类操作在**未产生随机结果前**可撤销 | 六边形战棋误点率极高，无撤销会造成强烈挫败。纪律 2 让这个功能几乎免费 |
| **腐蚀度影响明示**：地图界面显示"若现在遇到 Boss：HP +45%, ATK +30%" | 风险回报决策必须建立在完整信息上（Boss 位置可以藏，Boss 强度不能藏） |
| **Boss/精英房进入确认界面** | §9.3.3 的安全阀 |
| **动画速度设置 + 一键跳过** | 肉鸽玩家会玩几百小时 |
| **键鼠 + 手柄双支持**（六边形导航用 6 向） | Godot 下成本可控 |

### 13.3 战斗外界面

- **地图面板**：节点图 + **盲探迷雾（`?` 节点）** + 已探明计数 + 腐蚀度 + "当前 Boss 强度预览" + 线索提示区（§9.3.2）
- **角色面板**：6 属性（显示 基础值 / 碎片加成 / 装备加成 / 符文加成 的分解）、3 装备槽、**6 符文槽（可拖动重排，显示结算顺序）**、卡组浏览
- **符文实验室（可选但强烈建议）**：一个只读界面，列出当前 6 符文的**完整触发链**（"回合开始时：槽1 → 槽3 → 槽5"），帮助玩家理解自己的组合。这是 D6 的关键支撑 UI
- **拾取/替换界面**：新旧对比，明确高亮差异
- **层结算界面**：本层统计 + 三选一符文 + 容量提升 + 定向碎片分配
- **局结算界面**：路线回顾、**最终 6 符文 + 卡组展示（可截图分享）** ← 服务 D6 的社区传播
- **图鉴**：卡牌 / 符文 / 装备 / 敌人，含"已发现的符文组合"记录（可选，进一步服务 D6）

### 14.2 核心架构原则

| 原则 | 说明 |
|---|---|
| **逻辑与表现严格分离** | `src/core/` 中**不允许出现任何 Node / SceneTree 引用**。战斗可以在无渲染下跑完（这让 `tools/battle_sim.gd` 与全部单测成为可能） |
| **数据驱动优先** | 卡牌/符文/敌人/状态全部是 `Resource`，用 `EffectStep` 数组组合。**只有极少数特殊卡/符文**允许挂自定义脚本（`custom_script` 逃生舱） |
| **单一伤害管线** | `DamageCalculator.calculate()` 是全项目唯一算伤害的地方。任何"我在这里直接减 HP"的代码都是 bug |
| **单一坐标转换出口** | `HexCoord` 是唯一做坐标/旋转变换的地方（§8.1） |
| **单一占位校验出口** | `HexFootprint.can_place(grid, anchor, footprint, facing, ignore_unit)` 是唯一判定"能不能站这里"的地方。移动、生成、转向、推拉、召唤全部调它。**D8 的正确性完全依赖这一条** |
| **ActionQueue 作为唯一状态变更入口** | 纪律 2 |
| **TriggerBus 作为唯一触发分发入口** | D6 的组合正确性依赖统一分发 + 稳定顺序（符文按槽位、装备在符文后、状态最后） |
| **事件总线用于表现层** | 纪律 3 |
| **注入式 RNG** | 纪律 1 |

### 14.3 六边形网格的 Godot 实现

```gdscript
# TileSet 配置
tile_shape        = TileSet.TILE_SHAPE_HEXAGON
tile_layout       = TileSet.TILE_LAYOUT_STACKED           # odd-r 风格堆叠
tile_offset_axis  = TileSet.TILE_OFFSET_AXIS_HORIZONTAL   # 尖顶六边形
```

- 使用 **`TileMapLayer`**（Godot 4.3+；4.2 及以下用 `TileMap` + layer）。
- **多层结构**：`TerrainLayer` / `HazardLayer` / `HighlightLayer`（代码动态填充）/ `FeatureLayer`。
- 坐标：`TileMapLayer.local_to_map()` 给出 Godot 的偏移坐标 → **立刻**用 `HexCoord` 转成 `(col,row)` 与立方坐标。**禁止在业务代码里直接用 Godot 的 map 坐标。**
- 单位不是 tile，是独立 `Node2D`。位置 = `map_to_local(锚点)`，多格单位额外绘制 footprint 描边（`Line2D` 或 shader）。
- 排序：`y_sort_enabled = true`，让下方单位遮挡上方单位（俯视角必需）。多格单位的排序基准取 footprint 中 row 最小的格。

### 14.4 存档

| 存档 | 内容 | 时机 |
|---|---|---|
| **元存档** `meta.save` | 英雄等级、天赋、图鉴、难度阶层解锁、统计 | 每次变更立即写 |
| **局存档** `run.save` | 完整 `RunState`（seed、rng_states、层、腐蚀度、**盲探探明状态**、卡组、装备、**6 符文含顺序**、属性） | **每进入/离开房间时写**（房间粒度，不做战斗中存档） |
| **格式** | 开发期 JSON（便于调试），发布期二进制 `ResourceSaver` | |

> **战斗中不存档**：大幅降低复杂度。房间粒度对肉鸽足够（最多重打一场战斗）。
>
> ⚠️ **D4 的存档要求**：必须存"已探明哪些房间 / 已揭示哪些边"，否则读档后迷雾状态错乱。这是盲探系统容易漏的一点。

### 14.5 性能

回合制 + 49 格 + 少量单位 → 性能不是瓶颈。需注意：
- 高亮层用 `TileMapLayer.set_cell` 批量刷新，不要每帧重建
- 多格单位的 footprint 描边缓存，只在移动/转向时重算
- 伤害飘字用对象池
- `Database` 启动时一次性加载所有 `.tres` 并建索引（`Dictionary[String, Resource]`），运行时不做 `load()`

```gdscript
class_name HexFootprint
## 唯一的占位校验出口（§14.2）
static func cells(anchor: Vector3i, footprint: Array[Vector3i], facing: int) -> Array[Vector3i]:
    var out: Array[Vector3i] = []
    for off in footprint:
        out.append(anchor + HexCoord.rotate(off, facing))
    return out

static func can_place(grid: HexGrid, anchor: Vector3i, footprint: Array[Vector3i],
                      facing: int, ignore_unit_id: int = -1) -> bool:
    for c in cells(anchor, footprint, facing):
        if not grid.in_bounds(c): return false
        if not grid.is_walkable(c): return false
        var occ := grid.occupant_at(c)
        if occ != -1 and occ != ignore_unit_id: return false
    return true
```

```gdscript
@export var rule: GameRule
    # ENERGY_MAX / CARDS_DRAWN_PER_TURN / HAND_LIMIT / DECK_CAPACITY
    # CARD_COST_DELTA / FIRST_CARD_FREE / NO_DRAW_FIXED_HAND
    # SIZE_CLASS_OVERRIDE / KNOCKBACK_IMMUNE / BLOCK_PERSISTS
    # DAMAGE_MULTIPLIER / BLOCK_MULTIPLIER / CRIT_DAMAGE_MULTIPLIER
    # NO_BLOCK_ALLOWED / MOVE_COST_DELTA / EXHAUST_ALL_ATTACKS ...
@export var int_value: int
@export var float_value: float
@export var apply_order: int = 0             # 多个 override 冲突时的应用顺序
```

> **`RuleOverride` 是 D6 的核心武器**。`GameRule` 枚举会持续增长——每加一条就是一批新符文的可能性。**要求：每条 `GameRule` 在代码中只有一个消费点**（如 `ENERGY_MAX` 只在 `BattleFlow` 计算体力上限时读取），否则规则改写会产生难以追踪的 bug。
