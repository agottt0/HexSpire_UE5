# 内容管线架构：DataTable / DataAsset / 表现事件

本文定规范与约束。**每条约束都写了"为什么"**，因为这些规则的代价在违反后
几个月才会显形（静默失效、平衡被悄悄改动、打包才炸），到那时没人记得当初为什么这么定。

适用范围：四名英雄、全部敌人、敌人技能、卡牌、装备词条的配置管线，
以及技能释放后的 VFX / SFX / 动画表现。

---

## 0. 一句话结论

| 数据 | 载体 | 判据 |
|---|---|---|
| 逻辑数值（属性、射程、冷却、效果步骤） | **DataTable** | 要横向比较 |
| 表现资产（模型、动画、特效、音效、立绘） | **DataAsset** | 要拖资产、不比较 |
| 两者的接缝 | **`FName Id`** | 互不知道对方存在 |

不引入 GameplayTags，不引入 GAS。理由见 §7。

---

## 1. 为什么是两种载体，而不是统一一种

判据只有一条：**这份数据会不会被横向比较。**

调平衡的动作就是横向比较 —— 把四只怪的 HP 排成一列看曲线有没有跳变，
看 `MoveBudget` 的差异够不够体现"这只逼得多紧"。DataTable 的表格视图对此是刚需。
换成一怪一个 DataAsset，你得开四个窗口来回点，**看不出第三只的
`PreferredDistance` 比它的攻击射程还大** —— 而那个配错的后果是"这只怪整场只后退"，
在游戏里表现为一只怪很怪，但不报任何错。

美术资产反过来。没人会把四只怪的骨骼网格排成一列比较，
美术是一只一只配、配完就不动。DataAsset 在这里赢两点：

**① 引用语义。** DataTable 一旦加载，整张表所有行的引用一起进内存。
卡表已经踩过，用 `TSoftObjectPtr` 绕开了（见 `FHexCardVisualRow` 的注释）。
但怪物是骨骼网格 + 7 段动画 + 材质 + 特效，量级比贴图大一个数量级，
而且**软引用在 CSV 里没法往返** —— 路径是手打字符串，打错了静默变 null，
表现为 T-pose 或没特效，不报错。

**② 编辑器的类型检查。** 美术把 SkeletalMesh 拖进 DataAsset 的槽位，
有缩略图、有类型过滤、拖错了当场变红。填进 CSV 单元格就只是一串
`/Game/...`，和现在 `HexUnitAppearance.h` 里硬编码 `const TCHAR*` 的处境
几乎一样 —— 那个文件的注释自己说过，路径散开会得到"一堆资产找不到的静默失败"。

### 接缝：`FName Id`，双向都不知道对方

```
DT_Enemies（逻辑层这侧）                DA_Enemy_*（表现层那侧）
  RowName = siren                         DA_Enemy_Siren
  BaseHP / BaseATK / MoveBudget            SkeletalMesh + 动画集
  AIProfile / SkillIds                     受击特效 / 死亡特效 / 音效
        │ ToEnemyData()                              ▲
        ▼                                            │ 按 SourceId 查
  FHexEnemyData ──────────→ FHexUnit::SourceId ──────┘
```

`FHexEnemyData` 里**不允许出现任何资产字段**（纪律 3）。
`FHexUnit::SourceId` 是表现层唯一的查询键，它已经存在且已进 `Serialize`，
所以存档 / 回放自带它。

## 2. DataTable 侧规范

### 2.1 三件套模式（照抄卡牌，不要发明新形状）

卡牌管线已经跑通，每个新内容族照抄这三件：

| 件 | 卡牌的实现 | 职责 |
|---|---|---|
| 行结构 | `FHexCardTableRow`（`Source/HexSpire/Public/Data/`） | `UPROPERTY` 全暴露 + `ToXxxData()` / `FromXxxData()` |
| 加载器 | `FHexCardTableLoader` | 找表、校验行结构、逐行调 `Override*` |
| 导出 commandlet | `HexExportCards` | 把代码内建导成 CSV，给策划一个非空起点 |

**行结构必须放在 `HexSpire`（表现层）模块，不能放 `HexSpireCore`。**
`FTableRowBase` / `UDataTable` 属于 `Engine`。`HexSpireCore.Build.cs` 刻意只依赖
`Core` / `CoreUObject`，这是 12 个 Verify 套件与 10 万场批量模拟能在 headless 下
秒级重跑的前提。一旦 core 依赖 Engine，那套验证要先启动完整引擎 ——
一轮从秒级变成分钟级，而它的全部价值就在于"改完立刻能跑"。

### 2.2 代码内建是基线，表是覆写 —— 不要倒过来

```
HexContentLibrary.cpp 的内建数据   ← 权威基线，纯 C++，headless 可用
        ↓ 启动时
DataTable 同 RowName 的行           ← 整行替换该条
DataTable 新 RowName 的行           ← 追加为新条目
```

两个理由，都不是洁癖：

- 验证器与批量模拟不加载任何资产。数据只存在 `.uasset` 里的话，那套验证就废了。
- 表配错了、表丢了，游戏照样可玩，只是回到实测过的数值。比"启动就崩"好得多。

**覆写是整行替换，不是字段级合并。** CSV 导入时空单元格会填成类型默认值，
做字段级 diff 就得区分"没填"和"填了 0" —— DataTable 不保留这个信息，
于是"把冷却改成 0"会被当成"没填"而静默失效。

**`core` 自己永远不调用 `Override*`。** 只有表现层的加载器调。
这样 headless 拿到的始终是代码内建那套，不受配表状态影响。

### 2.3 要建的表

| 表 | 行结构 | 覆写入口 | 状态 |
|---|---|---|---|
| `DT_Cards` | `FHexCardTableRow` | `FHexContentLibrary::OverrideCard` | ✅ 已有 |
| `DT_Enemies` | `FHexEnemyTableRow` | `FHexUnitTableLoader::ApplyEnemyTable` | ✅ 已有 |
| `DT_EnemySkills` | `FHexEnemySkillTableRow` | `FHexEnemySkillLibrary::Override` | 入口已有，缺行结构与 loader |
| `DT_Heroes` | `FHexHeroTableRow` | `FHexUnitTableLoader::ApplyHeroTable` | ✅ 已有 |
| `DT_Runes` | `FHexRuneTableRow` | `FHexRuneTableLoader::Apply` → `FHexRuneLibrary::OverrideRune` | ✅ 已有（30 行）。⚠️ 必须在任何 RunState 建立前应用 —— RuneLoadout 持有指进符文库的裸指针 |

> ⚠️ `TArray<FName>` 在 CSV 里必须写成 `("a","b")` 数组字面量，
> **不能**用 `a|b` 之类自造分隔符 —— `FArrayProperty::ImportText`
> 要求单元格以 `(` 开头，否则整格解析失败、列静默变空数组。
> `DT_Cards` 首次建表时 `Tags` 就是这么全丢的（已由
> `migrate_card_table_column.py` 补回，导出器已改用数组字面量）。

英雄表是"四名角色"的真正前置。行结构（`FHexHeroTableRow`）与 loader
（`FHexUnitTableLoader`）已就位；法师那套「体力上限 −1，每回合抽牌 +2」
本身是两条 `FHexRuleOverride`，**在表里直接可配** —— 加新英雄只需在
`DT_Heroes` 加一行，不再碰 C++。

**起始卡组不单开表。** 它是英雄数据的一部分（一串 card id，挂在英雄行上）。
单开一张的话，"这张卡属于哪个英雄"就有两个真相来源了。

### 2.4 配表四条硬规则

**① RowName 必须等于 Id。** Id 是逻辑层认内容的唯一依据。
RowName 与 Id 不一致时，那一行会被当成**新条目追加**，而不是覆写 ——
表现是"我明明改了数值，游戏里纹丝不动"，且多出一条幽灵内容。

**② 数值走 §7.5 系数化三件套，别硬编码。**

```
最终值 = FlatValue + Stats[StatRef] × StatRatio
```

`Damage` 直接填 12 的内容，在 ATK 从 10 涨到 200 时会被数值冲垮，策略层失效。
例外是**离散量**（不随属性缩放）：状态层数、位移格数、抽牌数、体力数、冷却回合 ——
这些是策略锚点，填固定值才对。

**③ 枚举填标识名，不填中文。** `Attack` / `Guard` / `Move`，不是"攻击"。
CSV 导入按标识名匹配，填中文会**静默填成枚举第 0 项**，不报错。

**④ 空 FName 留空单元格，别写 `None`。**
`FName().ToString()` 的字面量就是 `"None"`，写进 CSV 再导回来会得到一个
**名字叫 None** 的 FName —— 于是 `StatusId` 非空，去找一个叫 "None" 的状态，
查不到就静默什么都不做。

### 2.5 ⚠️ 整行替换的最大陷阱：行结构加了字段，老表会把它冲成默认值

**这条是实测踩出来的，不是推演。** 加 `CastAnim` 字段时完整复现了一遍：

1. 给 `FHexCardData` 加字段，给基石卡配上值 → 代码里一切正确
2. 跑起来全是 `None` —— 因为 `DT_Cards` 里没有这一列，
   而覆写是整行替换，缺列的字段读出类型默认值并冲掉内建值
3. 症状是**"内建数据凭空丢失"**，查卡牌定义怎么看都是对的

更阴的是 **step 级字段**（`Effects[].VfxId`）：表里有 `Effects` 列，
只是列内每个 step 缺 `VfxId` —— 那是建表时导入的旧值。
顶层列检查抓不到它，症状与缺列一模一样。

**加字段时必须同步改三处**，漏任何一处都是静默失效：

| 改动点 | 漏掉的后果 |
|---|---|
| `FHexCardTableRow` 加 `UPROPERTY` | 表里根本没有这一列 |
| `ToCardData()` / `FromCardData()` | 表里有值但传不到逻辑层 |
| `HexExportCards` 的列名 + `Cols.Add` | 导出的 CSV 缺列 → 重导时又冲掉 |

**已有的防线（都是这次加的）：**

- `FHexCardTableLoader` 会检测「内建有值、表里全是默认值」的字段并告警，
  精确报出受影响的卡数与修法。
  ⚠️ 不要试图用 `GetColumnTitles()` 判断缺列 —— 它是**从 RowStruct 推导**的
  （引擎 `DataTable.cpp:973`），永远包含全部字段，与表里有没有这一列无关。
  UE 运行时不保留「导入时缺了哪些列」，只能用**数据本身**反推。
- `Tools/migrate_card_table_column.py` 做**字段级**迁移（JSON 往返，
  只改新列，保住美术的 `Visual` 组）。不能简单重导 CSV ——
  那会清空 `Visual`，而那些字段只存在于表里。

### 2.6 嵌套数组是括号字面量 —— 必须有断言兜着

`SkillIds` 这种 `TArray<FName>` 在 CSV 里写成 `("es_slam","es_stomp")`。
策划容易漏引号或漏括号，而**导入解析失败的表现是那一格变空，不报错**，
敌人于是静默退回 profile 默认攻击。

所以每个引用型字段都必须有引用完整性断言，见 §5。

## 3. DataAsset 侧规范

### 3.1 一只单位一个资产，按 `SourceId` 查

```
UHexUnitVisualSet : UPrimaryDataAsset
├── FName UnitId                    ← 必须等于 FHexEnemyData::Id / FHexHeroData::Id
├── 模型
│   ├── TSoftObjectPtr<USkeletalMesh> Mesh
│   └── TArray<TSoftObjectPtr<UMaterialInterface>> MaterialOverrides
├── 动画（按 EHexUnitAnim 分槽）
│   └── TMap<EHexUnitAnim, TSoftObjectPtr<UAnimSequence>> Anims
├── 表现参数
│   ├── float    MeshScale
│   ├── FRotator MeshRotation       ← 导入朝向不一致时用它纠，别改模型
│   └── FLinearColor RingColor      ← 留黑则回退到按威胁等级取默认色
└── 图鉴
    ├── TSoftObjectPtr<UTexture2D> Portrait
    └── TSoftObjectPtr<UTexture2D> CodexArt
```

**动画用 `TMap<EHexUnitAnim, ...>` 而不是 7 个具名字段。**
具名字段每加一个动画状态就要改结构、改 `PathFor` 的 switch、改所有资产 ——
而 `EHexUnitAnim` 是会长的（§13.2 要求玩家能从动作预判意图，
将来每只怪都要有自己的攻击动作）。Map 让「加一个状态」变成纯数据操作。

**为什么 `MeshRotation` 是资产字段而不是让美术改模型：**
外包模型的朝向千奇百怪。让美术回去改 FBX 重导一轮要一天，
在这里填 `Yaw=-90` 是十秒钟的事，而且改错了当场能看见。

### 3.2 特效资产也是 DataAsset，按 id 查

```
UHexVfxLibraryAsset : UPrimaryDataAsset
└── TMap<FName, FHexVfxEntry> Entries       ← key = 逻辑层的 VfxId

FHexVfxEntry
├── TSoftObjectPtr<UNiagaraSystem> System
├── EHexVfxAttach Attach      ← 世界格 / 施法者 / 目标 / 目标socket
├── FName   SocketName
├── FVector Offset
├── float   Scale
└── float   LifeSeconds       ← 0 = 由特效自己决定生命周期

UHexSfxLibraryAsset : UPrimaryDataAsset
└── TMap<FName, FHexSfxEntry> Entries       ← key = 逻辑层的 SfxId

FHexSfxEntry
├── TSoftObjectPtr<USoundBase> Sound
├── float VolumeMultiplier
├── float PitchMultiplier
└── bool  bAttachToSource     ← false = 在坐标处一次性播放
```

**为什么是「一个 Map 资产」而不是「一个 id 一个资产」：**
特效 id 在配表时是手打字符串（`vfx_slash`）。做成一资产一 id 的话，
拼错了要翻遍 Content 目录才能确认「到底有没有这个资产」。
集中成一张 Map，加载时能一次性把全部 key 打进日志，
**并让 VerifyContent 断言「表里引用的每个 VfxId 都在 Map 里」** ——
这条断言是「只需配置资产即可」能成立的关键，见 §5.3。

**为什么不把特效塞进单位资产：**
特效会跨单位复用（「斩击」是十几个技能共用的），
塞进单位资产等于每只怪各存一份引用，改一次要改十几个地方。

## 4. 技能释放的表现管线（VFX / SFX / 动画）

这是本次改动最实质的一块。**现状是断的**：`FHexEffectStep::VfxId` / `SfxId`
在 `HexCardData.h` 里存在、在卡表里可配、在 CSV 里能往返，
但**逻辑层从不把它们写进事件日志**；而表现层 `Tick` 里
`DrainEvents` 拿到事件后直接丢掉（`HexDemoGameMode.cpp` 那句
「目前只清空（灰盒期不播动画）」）。两头都有，中间没接。

### 4.1 铁律：逻辑不等待表现

```
逻辑（瞬时算完）                     表现（按自己的节奏）
ActionResolver 执行
  └→ State.LogEvent(...)  ──────→  DrainEvents
                                    └→ 推进播放队列
                                       ├→ 播动画
                                       ├→ 生成 VFX
                                       └→ 播 SFX
```

逻辑层**绝不**引用 Niagara / SoundBase / 任何渲染类型，也不等任何动画。
这不是洁癖：整场战斗要能在无渲染下跑完，否则批量模拟与全部验证器立刻失效。
「一键跳过动画」也因此是免费的 —— 把播放间隔设成 0。

### 4.2 事件必须携带表现意图，不能让表现层猜

现有事件名（`damage_dealt` / `unit_moved` / …）只说了**发生了什么**，
没说**该播什么**。让表现层从 `damage_dealt` 反推「该播哪个斩击特效」，
等于把配置权从策划手里拿走塞回代码 —— 与「只需配置资产即可」直接冲突。

所以 `FHexBattleEvent` 要加两个字段：

```cpp
FName VfxId;   // 取自触发本次效果的那个 FHexEffectStep
FName SfxId;
```

**为什么加专用字段而不复用 `NameA`：**
`NameA` 已被状态 id、卡 id 等占用，语义随 `Type` 变。再塞一个含义进去，
表现层就得写成「如果 Type 是 damage_dealt 则 NameA 是 vfx，否则…」——
这种按类型解释同一字段的代码每加一个事件类型就多一条分支，必然漏。

**填充点必须在效果执行处**（`ExecuteStep` 把 step 转成 action 时带上，
`ActionResolver` 写事件时透传）。在别处补会漏：一个技能有多个 step，
每个 step 各有自己的特效。

### 4.3 动画选择：数据驱动，不从事件类型硬推

该播哪个 `EHexUnitAnim`，由**技能自己声明**：

```
FHexEnemySkillData / FHexCardData
└── EHexUnitAnim CastAnim = EHexUnitAnim::Attack
```

理由是 §13.2 的硬要求：玩家要能从动作预判意图。
近战怪和法术怪都发 `damage_dealt`，若表现层一律播 `Attack`，
那条 UX 当场失效。而这个区分是**内容作者的决定**，不是引擎的推断。

### 4.4 播放队列：串行、可跳过、绝不回压逻辑

```
FHexVisualQueue（表现层，由 AHexDemoGameMode 持有）
├── Enqueue(const FHexBattleEvent&)   ← Drain 后逐条塞进来
├── Tick(DeltaSeconds)                ← 推进当前条目
└── SkipAll()                         ← 快速模式：全部瞬时结算
```

**为什么要队列而不是收到就立刻播：**
一张连击卡在同一帧产出 3 条 `damage_dealt`。立刻播的话三个特效叠在一起、
三声音效同时响，玩家看不出打了三下。队列让它们按 `HitCount` 依次呈现。

**为什么队列只能延迟表现、绝不能回压逻辑：**
一旦表现层能让逻辑「等一下」，确定性就没了 —— 同一个 seed 在两台机器上
因帧率不同产生不同结果，回放对不上，纪律 5 破。

### 4.5 三级回退链（和卡面美术同一套思路）

```
库里配了这个 id    → 用它
库里没有这个 id    → 打一条 Warning，不播，继续
连库都没加载       → 打一条 Warning（只打一次），全程不播
```

**缺资产绝不能让战斗中断或崩溃。** 灰盒期资产必然不齐，
「没有特效」要能和「有特效」共存，否则美术没交图的那几周游戏根本跑不起来。

**但每次回退都要留日志。** 静默回退的排查成本极高 ——
画面上只是「没看见特效」，你会先怀疑代码，
而真实原因可能只是 id 拼错一个字母。

## 5. 约束的机械化（本文最重要的一节）

**注释挡不住配表的人。** 现有代码里有一批只写在注释里的不变量，
配表开放之后它们会被违反，而且不报错。每条都要落成 `Verify` 断言。

### 5.1 引用完整性

| 断言 | 违反后的症状 |
|---|---|
| 敌人的每个 `SkillIds` 元素能在技能库查到 | 敌人静默退回默认攻击 |
| 每个 `StatusId` 能在状态库查到 | `ApplyStatus` 静默 no-op，效果凭空消失 |
| 英雄的每个 `CornerstoneCardIds` 能查到 | 角色没有基础动作，走不了路也打不了人 |
| 每个 `VfxId` / `SfxId` 能在特效库查到 | 技能放出来毫无表现 |
| 每个单位 id 有对应的 `UHexUnitVisualSet` | T-pose 或灰盒 |

### 5.2 数值合理性（现在只写在注释里）

| 断言 | 来源 | 违反后的症状 |
|---|---|---|
| `PreferredDistance <= 攻击射程` | `HexContentLibrary.h` 注释 | 敌人永远进不了射程，整场只后退 |
| `AttackRangeOverride != 1`（除非刻意） | 同上 | 该敌人永远产不出可躲型意图，§13.2 的「能躲/不能躲」区分消失 |
| 非离散量字段的 `StatRatio != 0` | §7.5 | 后期被数值冲垮，策略层失效 |
| 标签不产生任何加成 | §7.8 / §6.7 | 羁绊系统从后门长回来（D6 明令取消） |

最后一条现在**在四个头文件里各写了一遍，一个断言都没有** ——
它是全部内容纪律里防守最弱的一条。

### 5.3 完备性（照抄已有的两个成功例子）

`EHexGameRule` 有 `VerifyAllRulesHaveConsumer`，`EHexActionType` 有
`VerifyAllHandlersRegistered`，两者都遍历 `0..Count` 断言每个值都有落点。
这个模式要复制到两个现在没守卫的枚举上：

- **`EHexTriggerTiming`** —— ✅ **已有，而且是本项目防守最严的一处**，
  新增时机时照它的样子做即可。`FHexBattleFlow::GetTimingFireCount` +
  `VerifyTrigger::CheckTimingCoverage` 逐个时机装探针符文、跑真实战斗、
  看它有没有被触发。值得学的三个细节：
  豁免表是**白名单且每条必须写理由**（把「暂时没实现」塞进去就等于把缺陷合法化）；
  豁免表**必须用枚举名而不是数字**（第一版按记忆写数字，把 `OnBlockBroken`
  记成 8 实际是 9，结果豁免全打偏）；以及覆盖率之外还有三个**看结果**的
  端到端断言（《食魂》真的多抽一张、《焚心》真的挂上燃烧、《轮回护符》真的拿到格挡）——
  因为「时机被派发了」离「符文真的产生效果」还差过滤器、条件、限次、
  EffectOp 实现好几步，任何一环断掉符文依然是哑的，而覆盖率断言照样全绿。
- **`EHexEffectOp`** —— 现在有三个 dispatch switch（玩家 `ExecuteStep`、
  敌人 `ExecuteSkill`、符文产出路径），三者支持的 op 数已经不一致。
  漏一个不是编译错误，是运行时的 `unimplemented_op` 违规记录。

### 5.4 ✅ 事件名的单一声明处（已建 `HexBattleEventNames.h`）

事件类型名（`damage_dealt` 等 ~24 个）现在定义在
`HexActionResolver.cpp` 的**匿名命名空间**里，表现层拿不到 ——
只能自己手打一遍字面量。两边各写一份字符串，改名时必然只改一边，
表现为「某个动画突然不播了」且无任何报错。

已提到 `Source/HexSpireCore/Public/Battle/HexBattleEventNames.h`，
两侧共用同一组 `inline const FName`。

⚠️ 用 `inline const FName` 而不是宏或 `const TCHAR*`：
宏不带类型；`const TCHAR*` 每次比较都要构造临时 `FName`（字符串哈希），
而事件比较在 `DispatchTriggersForAction` 里是每动作每事件跑一遍的热路径；
`inline` 则保证 unity build 下跨编译单元只有一份实例，
不会撞 C2374「重定义」（`HexUnitAppearance.h` 顶部有同一个坑的完整记录）。

⚠️ 这些名字会进存档（事件日志用于回放），所以**改名是破坏性变更** ——
旧回放里的事件名不会随代码更新。

## 6. 分层纪律（改动时的红线）

```
HexSpireCore（Core + CoreUObject only）
├── 逻辑结构：FHexEnemyData / FHexCardData / FHexEnemySkillData
├── 允许出现：FName 形式的 VfxId / SfxId、EHexUnitAnim 枚举
└── 禁止出现：UDataTable / UDataAsset / UNiagaraSystem / USoundBase /
              USkeletalMesh / 任何 TSoftObjectPtr

HexSpire（表现层）
├── 行结构 + 加载器 + 导出 commandlet
├── DataAsset 定义与加载
└── 播放队列、特效生成、音效播放
```

**为什么 `VfxId` 可以留在 core：** 它只是一个 `FName`。逻辑层不解释它，
只把它从内容定义搬到事件日志。这与 core 已有做法一致 ——
逻辑层不知道 `vfx_slash` 是什么，只知道要把这个名字转交出去。
真正的红线是**不能出现资产类型或资产路径**。

**为什么 `EHexUnitAnim` 也可以：** 它是一个枚举，不引用任何资产。
让技能声明「我该播哪种动作」属于内容定义，而「那个动作是哪个 AnimSequence」
才是表现层的事 —— 前者进 core，后者进 DataAsset。

**枚举顺序是存档协议。** `EHexTriggerTiming` / `EHexEffectOp` 等
只允许在末尾追加，禁止插入或重排 —— 数字顺序是存档与确定性哈希的一部分。

## 7. 为什么不用 GameplayTags / GAS

### 7.1 硬理由

`GameplayTags` 模块依赖 `Engine` + `DeveloperSettings`，
而 `FGameplayTag` 的注册表要靠 `UGameplayTagsManager` 初始化（需要引擎启动）。
这会直接撞上 §2.1 那堵墙，废掉 headless 验证体系。

### 7.2 设计理由

tag 的价值在「开集、层级化、跨模块松耦合的分类查询」。
本项目的 ~25 条分类轴绝大多数是**闭集**：7 种卡类、3 种体型、3 个阵营、
9 种目标形状。枚举在这里更优，而且给了 tag 给不了的东西 ——
**完备性可以机械校验**（§5.3）。换成 tag 查询之后，查不到就是静默 no-op，
那类断言根本写不出来。

更关键的是，**驱动别人上 tag 系统的需求本项目已明确砍掉**：
§6.7 / D6 花了整节论证为什么不做羁绊 / 标签计数 / 套装加成，
还特意留了一句「避免以后又被加回来」。「数同标签个数」正是 tag 系统的主场。

剩下的 tag 职责（掉落加权、UI 筛选、图鉴分类、符文单条过滤）
`TArray<FName>` 全部够用，且已经在用。

### 7.3 拼错 tag 的防护用断言，不用下拉框

GameplayTags 的编辑器下拉框确实能防拼错。同样的保障用一份白名单 +
一条 `VerifyContent` 断言就能拿到，而且**比下拉框更强** ——
它同时管住 CSV 导入这条路径，而下拉框管不到 CSV。

另外现有 tag 的 key 是中文显示串（`TEXT("火焰")`）直接当键用。
GameplayTags 要求 ASCII 点分命名，迁移得先做 key/label 拆分，
而现有结构里没有地方放 label。

### 7.4 整个 GAS 更不要

现有的 ActionQueue + 注入式 RNG + 逐位确定性这套架构，
本质上就是 GAS 的替代品，而且是为了 headless 与可回放**刻意选的**。
GAS 绑 Actor / World、依赖预测与回滚、确定性不好保证。
两套并存会让「伤害」有两个真相来源 —— 这正是 `HexEnemySkillData.h`
顶部那段注释在防的事（同样配 1.0×ATK，卡牌打 13 敌人打 11）。

## 附：改完没生效时的排查顺序

配表类问题九成是静默失效，按这个顺序查最快：

1. 日志有没有「配表已应用：覆写 N 条」？没有 → 表没被加载，查路径。
2. 有「行结构不是 FHexXxxTableRow」→ 导入时选错行结构，重导。
3. `Overridden` 数比预期少 → 有 RowName 与 Id 不一致，那些行被当成新条目追加了。
4. 数值对但没有表现 → 查 `VfxId` / `SfxId` 是否在特效库的 Map 里（日志会列出全部 key）。
5. 敌人站着不动或只后退 → 查 `SkillIds` 解析（括号字面量）与 `PreferredDistance`。
